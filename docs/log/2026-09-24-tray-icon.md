# タスクトレイ（swing-tray）

デスクトップで使いやすくするために、Windows と macOS のタスクトレイ（メニューバー）から `swing up` を操作できるようにした。メニューは状態の表示、ダッシュボードを開く（ログインコード付き）、再起動、停止、起動、トレイを閉じる。構成の現状は [`../architecture/tray.md`](../architecture/tray.md)。

## 決めたこと

- **`swing up` に入れず、別のプロセスにした**:
  - `swing up` はサービス（systemd、launchd、`conhost --headless` 経由のタスクスケジューラ）として画面なしで動いていて、トレイを出せる GUI セッションにいるとは限らない。
  - トレイはイベントループをメインスレッドで回す必要があり、supervisor の作りと合わない。
  - 別プロセスなら、`swing up` が止まっていても「停止中」を表示して、そこから起動できる。
- **別のクレート（workspace のメンバー）にした**:
  - `swing` 本体に GUI の依存を入れずに済み、Linux の musl 静的ビルドがそのまま保てる。
  - Windows では `windows_subsystem = "windows"` が要る。`swing.exe` はコンソールアプリのままにしたいので、exe を分けた。
  - `swing` はもともと lib を公開しているので、トレイは `ApiClient`・`Config`・`login`・`service` をそのまま使う。
- **ダッシュボード API のクライアントにした**: `swing status` や `swing stop` と同じく、`dashboard.token` を読んで API を呼ぶだけにした。新しい API は足していない（`/api/overview`・`/api/login-code`・`/api/restart`・`/api/shutdown`）。
- **「停止」と「トレイを閉じる」を分けた**: 「終了」1 つだと、`swing up` が止まるのかトレイが消えるだけなのか分からないため。
- **「起動」はサービスの仕組みを通す**:
  - トレイが `swing up` を直接子プロセスにすると、トレイを閉じたときの扱いやログの出し先を別に決める必要がある。
  - なので、登録済みのサービスを起動するだけにした。そのために `swing service start` と `service::is_installed` を足した。
- **Linux は後回し**:
  - `tray-icon` の Linux 版は GTK と libappindicator が要り、musl の静的ビルドと合わない。
  - `ksni` なら Rust だけで書けるが、GNOME では拡張が無いと出ない。
  - GUI の依存は target 依存にして、Linux では「未対応」と出して終わるだけのバイナリにした。
- **表示の言語は OS のロケールで決める**: ダッシュボードがブラウザの言語で日本語と英語を切り替えるのに合わせた。
- **`schtasks` に `CREATE_NO_WINDOW`**: GUI サブシステムのプロセスからコンソールプログラムを起動すると、そのたびにコンソールウィンドウが開く。トレイは停止中に 5 秒ごとに `schtasks /Query` を呼ぶので、付けないと使えない。
- **多重起動の防止**: `swing.lock` と同じ `File::try_lock` で `<state_dir>/swing-tray.lock` をロックし、2 つ目のトレイは何も出さずに終わる。
- ポーリングの間隔は 5 秒。停止中のときだけ `is_installed` のために `schtasks` や `launchctl` を呼ぶので、それより短くはしなかった。

## 作ったもの

- `tray/`（`swing-tray`）: `status.rs`（状態から表示・使える項目・アイコンを決める純粋関数とテスト）、`worker.rs`（tokio でのポーリングと操作）、`app.rs`（tao と tray-icon）、`main.rs`（引数、多重起動の防止、未対応 OS のスタブ）、`assets/icon-64.png`（`web/favicon.svg` を ImageMagick で 64×64 に書き出したもの）。
- `src/login.rs`: `open` から `request_link`（URL とコードを返す）を切り出し、`open_browser` を公開した。
- `src/service.rs`: 各 OS の `start` と `is_installed`、Windows の `schtasks()`（`CREATE_NO_WINDOW` 付き）。macOS の `install` にあった「ロード済みか」の判定を `is_loaded` にまとめた。
- `src/main.rs`: `swing service start`。
- `.github/workflows/release.yml`: `--workspace` で lint とテストをし、Windows と macOS のアーカイブに `swing-tray` を入れる。

## ログイン時の自動起動

`swing service install` がトレイも登録するようにした。構成の現状は [`../architecture/service.md#タスクトレイの自動起動windows-と-macos`](../architecture/service.md#タスクトレイの自動起動windows-と-macos)。

- **既定で登録し、`--no-tray` で外す**: トレイを同梱する Windows と macOS では、`service install` した人の多くがトレイも欲しいはず、という判断。`swing` と同じディレクトリに `swing-tray` が無ければ飛ばすので、自分でビルドして `swing` だけを置いている人には影響しない。`--no-tray` を付けて入れ直したときは、既にある登録を消す。
- **登録した直後に起動する**: 次のログインまで待たずにトレイを出す。`--no-start` のときはサービスと同じく起動しない。
- **Windows は Run キー**: タスクスケジューラにも登録できるが、Run キーならタスクマネージャーの「スタートアップ アプリ」に出て、ユーザーが画面から無効にできる。トレイのような常駐アプリの普通の置き場所でもある。値は `reg.exe` ではなく `RegSetKeyValueW` で書く。`reg add /d` にすると、値に含まれる引用符を `reg.exe` がどう解釈するかに依存するため。`canonicalize` が付ける `\\?\` は外す。Explorer は Run キーの値を `CreateProcess` に渡すが、その形式のパスを受け付けるとは書かれていないため（タスクスケジューラの `conhost.exe` 経由では、実機で動くことを確かめてある）。
- **macOS は 2 つ目の LaunchAgent**: `LimitLoadToSessionType = Aqua` で、画面のあるログインのときだけ起動する。`KeepAlive` を付けないのは、トレイを閉じたなら次のログインまで出さないため。
- **トレイを `swing up` の親にする案は見送った**: Windows でトレイがログオン時に起動して `swing up` を子プロセスにすれば、`conhost --headless` の工夫は要らなくなる。ただ、トレイを閉じたときや落ちたときに `swing up` を巻き込むので、プロセスを分けた意味がなくなる。
- **`uninstall` は動いているトレイを止めない（Windows）**: macOS は `bootout` で止まる。Windows でトレイのプロセスを探して止めるのは、同じ PC のほかのユーザーのトレイを巻き込まない形で書く必要がある。なので、手間の割に得るものが無いと判断した。残ったトレイは「停止中（サービス未登録）」と表示するだけ。（後で変えた。トレイが登録の消滅を見つけて自分で閉じる。下記「uninstall でトレイが残る」）

検証: `launchd_tray_plist`・`tray_run_command`・`tray_exe_path` のユニットテストを足した。Linux と Windows（`cargo xwin clippy`）で clippy が通る。実機での登録は未確認。

## トレイを閉じるときの確認

Windows の実機で動かしてもらい、動くことを確かめた。そのときの指摘で、メニューの「トレイを閉じる」に確認のダイアログを足した。ダイアログには、閉じても SWING は動き続けること、トレイがいつまた表示されるかを書いている。

- ダイアログは `rfd` にした。Windows の `MessageBoxW` と macOS の `NSAlert` を直接呼ぶこともできるが、macOS の Accessory アプリでアラートを前面に出す処理（`rfd` の `FocusManager`）を自分で書くことになるため。
- ダイアログは別スレッドから出す。イベントループのハンドラの中でモーダルを回すと、ダイアログが開いている間、ハンドラが入れ子で呼ばれる（Windows）か、状態の更新が止まる。
- Windows の `rfd` は `MessageBoxW` に `MB_SETFOREGROUND` を付けない。メニューを押した直後は、トレイのプロセスが前面に出る権利を持っているので出る見込みだが、実機ではまだ確かめていない。

実機で試してもらい、ダイアログが前面に出ることを確かめた。そのうえで次の 2 点を直した。

- 停止中やエラーのときは、「トレイを閉じる」で確認しない。確認の文面は「SWING は動き続けます」なので、止まっているときに出すと話が合わない。
- 「停止」にも確認を足した。ミラーしているサイトの取得と配信が止まるうえ、サービスとして登録していなければトレイから起動し直せないため。

## 自動起動、終了の選択、操作の途中の表示

実機で試してもらった後の依頼で、次の 3 つを入れた。

- **トレイの起動時に、サービスとして登録済みで止まっていれば起動する**: 最初の状態の確認で 1 回だけ行う。その後に止まったのは、ユーザーが止めたのかもしれないので起動しない。ログイン時にサービスとトレイの両方から起動しても、2 つ目はサービスの仕組み（`IgnoreNew` と `kickstart`）と `swing.lock` で起動しない。
- **「トレイを閉じる」を「終了」に変え、SWING も止めるかを聞く**:
  - はい / いいえ / キャンセルの 3 択にし、ボタンの意味は本文に書いた。「SWING を停止してから閉じる」「トレイだけ閉じる」のような文字をボタンに付けるには、rfd の `common-controls-v6` 機能（`TaskDialogIndirect`）が要る。これを使うには、comctl32 v6 を指定したマニフェストを exe に埋め込まないと、起動時に関数が見つからなくなる。ビルドの仕組みを増やすほどの得は無いと判断した。
  - 「はい」は `swing stop` と同じ `stop::run` で、止まったのを確かめてから閉じる。止められなかったらトレイは残す。閉じた後に止まったかどうかを知る手段が無くなるため。
- **操作をしたら、すぐ表示を切り替える**:
  - 押した瞬間に「停止しています…」などに変え、その間は「終了」以外を無効にする。
  - 逆向きの操作（止めている途中の「起動」など）も、止まったのを確認するまでは有効にしない。タスクスケジューラの `IgnoreNew` のように、まだ動いているプロセスがあると、サービス側は起動の要求を無視する。すると止まりきった後に、止まったままになる。
  - 再起動は、押す前と違う `instance` を確認するまで「再起動しています…」のままにする。再起動の途中で API に一時的につながらなくなって、停止中と表示するのを防ぐため。
  - 途中の間は、状態の確認を 1 秒おきにして、切り替わりを早く拾う。その分 `service::is_installed`（`schtasks` や `launchctl` を起動する）は 30 秒覚えておくことにした。

検証: `Pending` の遷移と途中の表示のテストを足した（トレイのテストは 12 件）。Linux と Windows（`cargo xwin clippy`）で clippy が通る。`cargo test --workspace` の 1 回目に、`signer` のテストが 1 件だけ落ちた。今回の変更とは関係なく、再実行と、今回の変更を外した状態では通った。todo に積んだ。

## uninstall でトレイが残る

Windows で、トレイを起動したまま `swing service uninstall` すると、トレイが残った（Run キーの値を消すだけなので）。先に「動いているトレイは止めない」と決めていたが、実際に残ると、何が起きたのか分かりにくかった。

- トレイが登録の消滅を見つけて、自分で閉じるようにした。一度でも登録済みと確認した後で、登録が無いと確認したら閉じる。
- `uninstall` から外のプロセスを止める案は採らなかった。
  - 同じ PC のほかのユーザーのトレイを巻き込まないように、プロセスを選ぶ必要がある。
  - `TerminateProcess` で止めると、通知領域にアイコンがマウスを乗せるまで残る。
- 登録済みかどうかは、止まっているときだけでなく毎回調べることにした。止まってから確かめるのでは、`uninstall` が SWING を止めてから登録を消すまでの間に確かめた結果（まだ登録済み）を覚えてしまうため。代わりに、覚えておく時間を 30 秒から 10 秒に縮めた。
- 登録済みかどうかは、設定ファイルを読む前に調べる。読めなかったときに「登録なし」として扱うと、swing.toml を書きかけで壊しただけでトレイが閉じてしまうため。

検証: `RegistrationWatch` のテストを足した（トレイのテストは 13 件）。Linux と Windows（`cargo xwin clippy`）で clippy が通る。実機では未確認。

文言の見直し: 「終了」の確認を「SWING を停止してからトレイを閉じますか？」に短くし、「いいえ」ならトレイだけを閉じることを 1 行添えた（質問だけだと、「いいえ」がトレイを閉じないことなのか分からないため）。止まるのを待っている間の表示は、専用の「停止してから終了します…」をやめて、「停止」と同じ「停止しています…」にした。

レビューでの指摘: 署名アプリの失敗の表示を「動作中（署名アプリが応答しません）」から「動作中（前回の署名に失敗しました）」に直した。`signer.last_failure` は時間切れだけでなく、署名アプリでの拒否や接続できないときにも入り、次に署名が成功するまで残るため。ダッシュボードの Publish 画面の「署名アプリへの最後のリクエストが失敗しました」に合わせた。
