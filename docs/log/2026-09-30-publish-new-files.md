# 公開の前に増えたファイルを確かめる・シークレットスキャンの案内

セキュリティレビューの後に todo へ積んだ、公開の安全性を高める 2 つ（[2026-09-30](2026-09-30-review-followups.md)）を片付けた。これまでの publish の確認は SWING 自身の秘密・サイトの外へのシンボリックリンク・ドットファイル・サイズだけで、`id_ed25519` や `secrets.json` のような、ドットで始まらない名前の秘密は素通りだった。

## 決めたこと

- 増えたファイルは「relay 上の自分の最新版に同じパスが無いファイル」とした。中身が変わっただけのファイルは出さない。更新のたびに全ファイルを出すと読まれなくなるので、見るべきものだけに絞った。
- 前の版は、relay から取った自分の最新のサイトイベントの CID を、Kubo でオフラインに（ローカルのブロックだけで）たどって一覧する。
  - MFS に残っている最新の版を使う案もあったが、relay に受理されなかった版も MFS には残るので、公開していない版と比べてしまうことがある。relay 側なら公開した版と比べられる。
  - relay が新しい版を隠して古い版を返しても、増えたファイルが多めに出るだけで、見逃す側には倒れない。署名は自分の鍵なので偽の版は作れない。
  - オフラインにしたのは、別のマシンで publish した版を探しにネットワークへ出て止まらないため。一覧できなければ前の版が無いものとして扱う。
- 前の版が無い・読めないときは、全ファイルを増えたファイルとして出す（件数と大きいものだけにする案もあったが、確かめる目的からは全件が要る）。CLI は先頭 50 件と残りの件数、ダッシュボードは全件をスクロールで出す。パスの文字順に並べると `index.html`・`sss/index.html`・`testekey` のように同じフォルダのファイルが離れるので、ルート直下を先に、続けてフォルダごとにまとめて出す。フォルダは木にせず、親のパス全体（`a/b/`）を 1 つのまとまりにした（入れ子が深くても字下げが増えない）。
- CLI の確かめ方は、端末なら `y/N` で聞き、`--yes`（`-y`）で聞かずに通す。端末でないとき（CI など）に `--yes` が無ければ止める。一覧を出して続ける案もあったが、誰も読まないログに出すだけでは確認にならないので止める側にした。増えたファイルが無ければ聞かないので、中身を書き換えるだけの更新は今まで通り CI で通る。
  - このため、端末の無い環境でファイルを足す publish をしているスクリプトは `--yes` を足す必要がある。デモ環境の `seed.sh` には足した。
- 他の確認と同じ `off`/`warn`/`require` のモードにする案もあったが、ファイルを足すたびに止まる `require` は普段の更新で邪魔になり、`warn` では見るだけになる。人が見て決めることなので、対話の確認と `--yes` にした。
- ダッシュボードは、ブラウザがアップロードの前にファイルの一覧を持っているので、前の版の一覧を返す `GET /api/publish/previous-files` を足し、差分はブラウザで出す。アップロードしてから確かめる 2 段階の API にすると、受け取ったファイルを確認が済むまでサーバに置いておく必要があり、後片付けとタイムアウトが増える。`/api/publish/upload` 自身は確認を経たかを見ない（ログインした本人の画面なので、飛ばして困るのは本人だけ）。
- relay への接続と前の版の取得を add の前へ移し、同じ内容かどうかの確認（add の後）もこの結果を使うようにした。relay に 2 回問い合わせない。
- シークレットスキャンは SWING に組み込まず、site-guide で gitleaks・TruffleHog・detect-secrets を、publish の前に出力先のディレクトリへ実行する外部ツールとして紹介した。スキャナは既知の形式しか見つけられないので、増えたファイルの確認と組み合わせるよう書いた。

## 作ったもの

- `ipfs::list_files_local`: `ls`（`resolve-type=true&offline=true`）でディレクトリを 1 つずつたどり、ファイルのパスを名前順で返す。項目の数に上限（publish では 100 000）を付けた。
- `publish::PreviousFiles`（`src/publish/new_files.rs`）: 前の版の一覧・増えたファイルの計算・CLI の表示。
- `swing publish --yes`。`publish::run` の引数が多くなったので `publish::Request` にまとめた。
- `GET /api/publish/previous-files?site=<d>` と、公開画面の確認パネル（`#publish-confirm`、`.swing-file-list`）。

## 検証

- ユニットテスト: 増えたファイルの計算、表示の上限、`ls` をたどる処理（偽の Kubo で、入れ子・HAMT・上限超え）、API の `site` の検証。
- 実 Kubo 0.43.1 の統合テスト（`#[ignore]`）: 入れ子のディレクトリと、HAMT に分割されたディレクトリ（200 文字の名前 1 500 件で分割されることを `dag get` で確かめた）を一覧でき、ローカルに無い CID と上限超えはエラーになる。
- デモ環境の CLI: 前の版が無いとき全件を出し、端末でなければ `--yes` 無しで止まる。ファイルを足すと増えた分だけが出て、`n` で止まり `y` で公開する。同じ内容なら `no new files` の後に `Unchanged; not published.` になる。
- デモ環境のダッシュボード（英語と日本語）: 増えたファイルがあるとパネルを出し、キャンセルでは送らず、「このファイルを含めて公開」で公開する。前の版が無いサイトでは全件を出す。同じ内容のときはパネルを出さずに送る。

## 見つけたこと
