# ミラーに追加する前にフィンガープリントを出す

「ミラーに追加」（Sites 画面と Desktop 画面のダイアログ）は、応答も結果の表示も npub だけで、入力した鍵の絵文字のフィンガープリントは追加した後に Sites 画面に出るまで見えなかった。相手の画面と見比べてから追加できるよう、入力中に鍵ごとに出す。

## 決めたこと

- `POST /api/mirror/preview` を足した。`mirror/add` と同じ `{ "keys": [...] }` を受けて、入力ごとに `input`・`npub`・`fingerprint` を返す。`mirror/add` の応答にフィンガープリントを足す案もあったが、それでは追加した後にしか見えないので別の API にした。
- フィンガープリントは pubkey だけで決まるので、relay も Kubo も引かない。agent の準備やセットアップモードに関わらず応答し、relay を引く API の同時実行の枠も使わない。ミラー済みかどうかは Follow Set を引かないと分からないので返さない。
- 入力中に呼ぶので、読めない鍵があっても全体を 400 にせず、その鍵だけ `npub`・`fingerprint` を `null` にする。空と件数の上限超えは `mirror/add` と同じく 400。同じ pubkey の 2 件目以降は `mirror/add` と同じく落とす。
- 画面は入力のたびに 250ms 待ってから呼び、古い要求の応答は捨てる（`ui.js::createKeyPreview`。Sites 画面と Desktop 画面で共有）。
- 入力が空のときも行を消さずに「ここにフィンガープリントとnpubが表示されます。」を出し、鍵の行・読めない鍵の行と同じ高さにした。入力を始めたときや消したときに、下の要素が動かない。
- Desktop 画面では、Twemoji のベクタのままだと画面のドット絵の見た目から浮くので、16×16 に縮めて不透明度を 2 値にしたドット絵にした（`desktop-fingerprint.js`）。ほかに、縮めたまま（ふちがぼける）・さらに色の段階を減らす・Win16 の 16 色・12×12 を並べて比べた。16 色は淡い色や細い線の絵文字が消え、12×12 は絵柄を見分けにくかった。
- ドット絵は画像を別に持たず、ブラウザの canvas でスプライトから描く。表やスプライトを変えたときに作り直すものが増えず、Twemoji の版と食い違わない。canvas を読めないときはその絵文字だけベクタに戻す。
- 256 個を全部ドット絵にして並べると、元の絵柄はほぼすべて見分けられた。地の色の影響も見た。Twemoji の白は薄い灰色（#e1e8ed 前後）なので、ひつじ・雲・にわとりはダイアログの地（#c0c0c0）より明るく浮いて見え、読み取り専用の入力欄の地（#dfdfdf）ではほとんど消えた。うさぎ・ねずみ・フォーク・指輪などの中間の灰色は #c0c0c0 では弱いが、形は分かった。初めは白いくぼんだ枠に置いたが、入力欄のように見えて何の枠か分かりにくかったので、枠を外してダイアログの地にじかに並べた（#dfdfdf の読み取り専用の枠にする案は、白っぽい絵文字が消えるので採らなかった）。トカゲ・恐竜・ドラゴン、スペード・クラブなどの似た組はベクタのときから似ていて、ドット絵にしたことで新しく生まれた紛らわしさは見当たらなかった。

## 検証

- `cargo fmt`・`cargo clippy`・`cargo test` が通った。`/api/mirror/preview` のテストは、セットアップモードで応答すること・読めない鍵と重複の扱い・空と上限超えの 400 を確かめる。
- デモ環境で、Sites 画面の入力欄に hex・読めない文字列・npub・同じ鍵の hex を入れ、重複を除いた 3 行（読めない鍵は赤字）が出ること、Desktop 画面のダイアログで同じ鍵に同じ絵文字のドット絵が出ることを確かめた。両方で、空・読める鍵 1 つ・読めない鍵 1 つのときの行の高さが同じ（Sites 画面 30.5px、Desktop 画面 20px）で、ダイアログの高さも変わらないことを測った。
- スプライトから canvas に描いて読み戻す処理が、Chromium・Firefox・WebKit（Playwright）で動くことを、同じ手順の試作のページで確かめた（Firefox と WebKit ではダッシュボード上では見ていない）。
