# 2026-09-25 Desktop 画面のフォーカス・キーボード操作の統一

## 対応した項目

Desktop 画面（SWING Explorer ウィンドウ・「コントロール パネル」ダイアログ・デスクトップアイコン・タスクバー）でキーボード操作とフォーカス表示がバラバラだったのを揃えた。

1. デスクトップアイコンをクリック/Enter で開いた後、開いたウィンドウ/ダイアログが実際にフォーカスを受け取ったらアイコンの選択状態（紺地ハイライト）を解く。
2. フォーカス表示（Win95 風の 1px 点線矩形）をデスクトップ内のすべての実機能コントロールで統一し、ブラウザ既定の青いフォーカスリングを一掃した。
3. Desktop 画面全体（アイコン・ウィンドウ・iframe 内のリンク・タスクバー）を 1 つの Tab トラップにまとめ、サイドナビやブラウザ本体へ出ないようにした。iframe の中は別ドキュメントなので専用の継続処理を足した。Esc での脱出手段（サイドナビの Desktop リンクへ）も用意した。
4. ウィンドウとダイアログの間で食い違っていた挙動（後述の監査結果）を洗い出し、明確な不整合は直した。

## 決めたこと

| 決定 | 理由 |
|---|---|
| ウィンドウ/ダイアログにフォーカスが入ったらアイコンの選択を解く実装は、開く操作のたびに明示的に呼ぶのではなく `focusin` を使う | 開く経路（ダブルクリック／Enter／将来増えるかもしれない経路）を全部把握して個別に解除コードを書くより、「フォーカスが実際にそこへ入った」という 1 つの事実にだけ反応するほうが確実で、今後のコード追加にも自動的に効く |
| ウィンドウのアクティブ/非アクティブなタイトルバーは、ダイアログが既に持っていた `.is-inactive` クラスとその CSS（明滅にも使っている）をそのまま流用し、セレクタを `.desk-dialog-titlebar.is-inactive` から `.desk-titlebar.is-inactive` に一般化しただけで済ませた | 新しいクラス名を増やすと「ウィンドウ用」「ダイアログ用」で 2 つの見た目を別々に管理することになり、今回直したかった「2 つの間の不整合」を再生産してしまう。既存のクラスがどちらのタイトルバーにも付いている（`class="desk-titlebar desk-dialog-titlebar"`）ことを確認した上でセレクタだけ広げた |
| フォーカス表示は基本 `1px dotted #000000` の inset に統一しつつ、デスクトップアイコン（白）・背景色のスウォッチ（外側）・カスタムカラー入力（外側）の 3 つだけ意図的に外側/色を変える | デスクトップアイコンはテール地に黒が沈むため元から白（既存の設計をそのまま維持）。スウォッチはパレットの色そのものが背景になるため、暗い色（黒・紺など）の上に黒の点線を inset で乗せると本当に見えなくなる（実機で確認して気づいた）。カスタムカラー入力も同じ理由。どちらも色は同じ黒のまま、outline の位置だけ外側にして解決した（コントラストの問題であって、線の太さ・種類を変える理由ではないため） |
| iframe（リンク集ページ）内のリンクにも同じ `1px dotted #000000` を `desktop-page.css` 側に追加した | 「デスクトップ内のすべての実機能コントロールで統一」という要求は、リンク集ページのリンクが見た目上ウィンドウの中身である以上、そこも含むと判断した。iframe は別ドキュメント・別スタイルシートなので、親側の CSS 変更では届かず、ページ側にも同じ値を書く必要がある |
| ウィンドウ・ダイアログの外枠自体には `:focus-visible` の点線矩形を付けない（`tabindex="-1"` で `.focus()` の的にはなるが、視覚的には何も出さない） | Win95 の実機はウィンドウ全体を枠で囲む代わりにタイトルバーの配色（アクティブ/非アクティブ）で「どれが最前面か」を示す。ここに点線矩形まで足すと二重の表現になり、かえって Win95 らしくなくなる |
| デスクトップ全体の Tab トラップは、ダイアログが開いている間は完全に無効化し、ダイアログ自身の（前から実装済みの）より狭いトラップだけに任せる | 2 つのトラップ実装が同時に Tab を奪い合うと、どちらが勝つかの調整が複雑になり壊れやすい。「デスクトップ全体」と「モーダル 1 個」は同時に有効である必要が無い（モーダルは常にデスクトップの一部を覆っているだけ）ので、片方が開いている間はもう片方が完全に黙る、という単純な排他にした |
| iframe 内で Tab/Shift+Tab が境界（先頭/末尾のリンク）に達したときの継続処理は、iframe 側のドキュメントにも同じ内容のキーボードリスナーを別途張ることで実現した | 同一オリジンの iframe でも `keydown` は親ドキュメントへバブルしない（別ドキュメントなので）。親側だけにリスナーを置いても iframe の中で起きたキー操作は一切見えないため、境界の継続処理だけは iframe 側に置く必要がある。ページは差し替え可能な設計（`desktop-page.html`）なので、ページが読み込まれるたびに張り直す既存の仕組み（`wirePageFrame` の `onLoad`）に相乗りさせた |
| Esc の脱出先はサイドナビの「Desktop」リンク（今まさに見ている画面自体のナビ項目）にした | どこか別の画面に飛ばすと「閉じ込められていたと思ったら今度は画面が変わった」という別の驚きを生む。同じ画面に留まりながらデスクトップの外（サイドナビ）へ出る、という最小の変化にした |

## 監査結果（ウィンドウ ⇄ ダイアログ ⇄ デスクトップの不整合を洗い出したもの）

| 項目 | 状態（直したか／意図的に残したか） |
|---|---|
| アイコン選択のクリア | **直した**（上記「対応した項目」1）。今までは「デスクトップの余白をクリックしたときだけ」解除され、開いた後は残り続けていた |
| フォーカス表示（`:focus-visible`） | **直した**。ツールバーの「更新」ボタンだけ `2px solid #000000; outline-offset: 1px` という別系統のスタイルが付いていて、他（タイトルバーのボタン・タスクボタン・ダイアログのタブ/ボタン/コンボボックス）とバラバラだった。背景色のスウォッチとカスタムカラー入力にはフォーカス表示が一切無く、ブラウザ既定の青いリングが出ていた。すべて `1px dotted #000000`（またはコントラスト上の理由がある 3 箇所だけ位置/色を変えた版）に揃えた |
| タイトルバーのアクティブ/非アクティブ | **直した**。ダイアログには「外側クリックで明滅する」ための `.is-inactive` があったが、実際にフォーカスが移動したときの状態追従は無く、明滅が終われば常にアクティブ色に戻っていた。ウィンドウ側にはこの概念自体が無く、常にアクティブ色（ネイビー）のままだった。両方に `focusin`/`focusout` ベースの追従を足し、セレクタも共通化した |
| Tab トラップの範囲 | **直した**（上記「対応した項目」3）。今まではダイアログが開いているときだけトラップがあり、デスクトップ本体（アイコン・ウィンドウ・iframe・タスクバー）には無かった |
| ウィンドウを閉じる/最小化したときのフォーカスの行き先 | **直した**。ダイアログはキャンセル/OK/×/Esc のどれで閉じてもアイコンにフォーカスを戻していたが、ウィンドウの閉じるボタンはフォーカスをどこにも移しておらず、閉じた（`hidden` になった）ボタンにフォーカスが残ったままになっていた（キーボード操作が事実上そこで止まる不具合）。最小化も同様（最小化ボタン自身が隠れる）。閉じる→ SWING Explorer アイコン、最小化→タスクボタン、にそれぞれ移すようにした |
| 開くときにウィンドウ/ダイアログへフォーカスを移すか | **直した**。ダイアログは元から `openDialog()` で `.focus()` していたが、ウィンドウは（ダブルクリックでもキーボードの Enter でも）フォーカスをどこにも移していなかった。`#desk-window` に `tabindex="-1"` を足し、開く/復元するたびに `.focus()` するようにした |
| キーボード活性化（Enter / Space） | 監査したが**問題なし**。デスクトップアイコン 2 個はどちらも Enter/Space に対応済みで揃っている。実際のボタン類（`<button>`）はブラウザ既定の Enter/Space 活性化に任せているだけで、こちらも自然に揃っている |
| ホバー時の見た目 | 監査したが**問題なし**。実際に押せるボタン（タイトルバーのボタン・タスクボタン・ダイアログのボタン・タブ・コンボボックス・スウォッチ）はどれも `:hover` を持たない（Win95 の実機に合わせた元々の設計。装飾のメニューバー/ツールバーだけがホバー反応する）。ウィンドウ側とダイアログ側で扱いが割れているということは無かった |
| 押した瞬間の沈み込み（`:active`） | 監査したが**問題なし**。タイトルバーのボタン・「更新」・ダイアログのボタン・コンボボックスは `:active` の沈み込みベベルを持つ。タスクボタンとスウォッチは持たないが、これらは瞬間的な押下ではなく `is-active`/`is-selected` という持続的なトグル状態で見た目を変える設計なので、`:active` が無いこと自体は妥当と判断し、追加しなかった |
| カーソルの形 | 監査したが**問題なし**。`#view-desktop` 全体が `cursor: default` を継承し、実際に押せる要素にも `pointer` を付けない（Win95 の実機に合わせた既存の設計）という方針が全コントロールで一貫していた |
| テキスト選択 | 監査したが**問題なし**。`user-select: none` は `#view-desktop` の 1 箇所だけに書かれていて、ダイアログもその子孫として自動的に継承している。iframe（別ドキュメント）だけは元から選択可能なままで、これは意図通り |
| 文字サイズ | 監査したが**問題なし**。`desktop.css` 内の `font-size` 宣言はどれも 12px（来訪者カウンタだけ例外というのは既存のドキュメント通りで変更なし） |
| ベベルの描き方 | 監査したが**問題なし**（過去のレビュー往復で既にタブ/パネルとも `.desk-window` と同じ 4 層ベベルに揃えてある） |
| z-order・最前面化 | **対象外**。ウィンドウは 1 枚しか存在せず、重なり順を切り替える別ウィンドウが無いので、クリックで最前面に持ってくるような処理自体が意味を持たない |
| 閉じる操作の意味 | **意図的に残した差**。ウィンドウの × は「閉じた状態」を保持し、アイコンから明示的に開き直すまで戻らない。ダイアログの ×/キャンセル/Esc は単に非表示にするだけで、いつでもまた開ける。これはアプリのウィンドウと一時的な設定パネルという役割の違いによるもので、フォーカスやビジュアルの不整合ではないため統一しなかった |

## 実装

- `web/desktop-window.js`: `closeWindow()`/`minimizeWindow()` がそれぞれ SWING Explorer アイコン/タスクボタンへフォーカスを戻すようにした。`openWindowFromIcon()` の最後で `#desk-window` へフォーカスする。`#desk-window` に `focusin`/`focusout` を追加し、アイコンの選択解除とタイトルバーのアクティブ/非アクティブ追従をする。
- `web/desktop-settings.js`: `#desk-dialog-control-panel` に `focusin` を追加してアイコンの選択解除をする。`DesktopSettings.isDialogOpen()` を新たに export し、デスクトップ全体のトラップから「今モーダルが開いているか」を問い合わせられるようにした。
- `web/desktop.js`: デスクトップ全体の Tab トラップ（`onDesktopKeydown`、`document` の capture）と、iframe 側の継続処理（`onFrameKeydown`、ページ読み込みのたびに張り直す）、Esc の脱出処理（`escapeDesktopToSideNav`）、フォーカス対象一覧の組み立て（`outerDesktopFocusable`/`innerDesktopFocusable`/`combinedDesktopFocusable`）を追加した。
- `web/index.html`: `#desk-window` に `tabindex="-1"` を追加。
- `web/desktop.css`: `.desk-dialog-titlebar.is-inactive` → `.desk-titlebar.is-inactive` に一般化。ツールバー「更新」ボタンのフォーカス表示を他と同じ `1px dotted` に統一。背景色のスウォッチとカスタムカラー入力にフォーカス表示を追加（コントラスト対策で外側の `outline-offset`）。
- `web/desktop-page.css`: リンク集ページのリンクに同じ `1px dotted #000000` のフォーカス表示を追加。

後方互換のための処置は入れていない（挙動の変更のみで、保存データの形は変わらない）。

## 追記: レビュー指摘の対応（同日、f2 ラウンド）

上記の実装に対するレビューで指摘された 3 件に対応した。

### 1. `tabindex="-1"` のコンテナ（ウィンドウ/ダイアログ）にブラウザ既定の青いフォーカスリングが出ていた

前ラウンドの検証はダブルクリックなど主にマウス操作で `.focus()` を経由させていたため `:focus-visible` が発火せず、見落としていた。実際にキーボード（アイコンにフォーカスして Enter）で開くと、`#desk-dialog-control-panel` と `#desk-window` のどちらも `outline` を明示していなかったため、ブラウザ既定の青い `outline: rgb(6, 69, 173) solid 2px` が出ていた。

`web/desktop.css` に以下を追加して修正した。

```css
#desk-window:focus-visible,
.desk-dialog:focus-visible {
  outline: none;
}
```

内側の実コントロール（ボタン・タブ・コンボボックス等）には `outline` を個別に指定済みで、この宣言はコンテナ自身のセレクタにしか掛からないため、内側の点線矩形には影響しない。

検証（完全再起動後、実際に Tab/Enter でキーボード操作してから `getComputedStyle` と `:focus-visible` のマッチを確認）:

- ダイアログ: `{"outline":"rgb(0, 0, 0) none 0px","matchesFV":true}`
- ウィンドウ: `{"outline":"rgb(0, 0, 0) none 0px","matchesFV":true,"active":"desk-window"}`

どちらも `:focus-visible` は真のままリングは出ない。ズームしたスクリーンショットでも縁に青いリングが無く、Win95 の通常のベベルのみであることを確認した。

### 2. iframe 内の最初のリンクのフォーカス表示が「丸い実線の黒いリング」に見えた

ブラウザを完全に再起動した状態から、アイコン→ Enter →ウィンドウ内を実際に Tab で辿って iframe 最初のリンク（「BOB ZINE 電子版」）にフォーカスさせ、`getComputedStyle` と `:focus-visible` を確認したところ `outline: rgb(0, 0, 0) dotted 1px`・`matchesFV: true` で、`desktop-page.css` の `a:focus-visible` の指定どおり正しく点線矩形が出ていた。

ズームしたスクリーンショットで実際にピクセルを見ると、指摘の「丸い実線の黒いリング」ではなく点線の四角形であることが確認できた。同じリンクをフォーカスしていない状態のスクリーンショットと並べると、太字・下線・青色のビットマップフォントのリンク文字自体が小さいサイズで拡大されると黒っぽい塊に見えることが分かり（フォーカス有無に関わらず文字の見た目は同じ）、指摘は文字のレンダリングをリングと読み違えたものだったと判断した。コードの修正は行っていない。

### 3. コメントを 1 行の理由書きに絞る

`git diff -U0 -- web | grep -E '^\+' | grep -E '/\*|//'` で洗い出し、複数行の説明になっていたコメントをすべて 1 行の「自然な実装を避けた理由」だけに削った。最終的に残っているのはこの 6 行のみ。

```
/* Matches desktop.css's dotted focus rectangle; a separate document needs its own copy. */
/* Win95 shows active/inactive via the titlebar, not a ring around the whole window. */
/* Outside, not inset: inset would be invisible against the darker palette colors. */
/* Not `[href]`: that also matches the decorative SVG `<use href>` icon references. */
/* Defers entirely to the dialog's own tighter trap (desktop-settings.js) while it's open. */
/* A separate listener because same-origin iframes still don't bubble keydown to the parent. */
```

## 追記: タイトルバーのアクティブ/非アクティブのバグ修正（同日、f3 ラウンド）

ユーザー報告で 3 件のバグが見つかった。

1. SWING Explorer の中身（iframe）をクリックするとウィンドウのタイトルバーが非アクティブになる（iframe はウィンドウの一部なのでアクティブのままであるべき）。
2. ウィンドウがアクティブに見えている状態でアイコンのダブルクリックから「コントロール パネル」を開いても、ウィンドウのタイトルバーが非アクティブにならない（ダイアログが開いている間は非アクティブであるべき）。
3. デスクトップの背景をクリックすると非アクティブになる（これは正しい挙動で、そのまま維持）。

### 原因

これまでの実装は `#desk-window` の `focusin`/`focusout` の差分（イベントごとの前後比較）で `.is-inactive` を付け外ししていた。これが 2 つの理由で壊れていた。

- iframe へ実際にフォーカスが移ると、親ドキュメントの `focusout` は `relatedTarget` が `null` になる（別ドキュメントをまたぐフォーカス移動はブラウザが `relatedTarget` を設定しない）。既存のコードは `relatedTarget` がウィンドウの中かどうかでしか判定していなかったため、`null` の場合を「ウィンドウの外へ出た」と誤判定し、非アクティブにしてしまっていた（1 の原因）。
- ダイアログを開く直前にウィンドウ自身が実際にフォーカスを持っていなかった場合（例えばアイコンをダブルクリックした瞬間はアイコン自身にフォーカスが移ることがある）、`#desk-window` の `focusout` はそもそも発火せず、非アクティブへ切り替わる機会が一度も無かった（2 の原因）。

### 修正の方針

差分ベースをやめ、「今どこに実フォーカスがあるか」から毎回タイトルバーの状態を導出する方式に置き換えた。

- `DesktopWindow.syncActive()`: `winEls.win.contains(document.activeElement) && !DesktopSettings.isDialogOpen()` でアクティブかどうかを決め、`.is-inactive` を付け外しする。iframe に実際のフォーカスが移ると親ドキュメントでは `<iframe>` 要素自体が `document.activeElement` になる（既存の DOM の仕組みで、iframe はウィンドウの子要素なので `contains()` が自然に真になる）ため、1 の原因は特別扱いなしで解消する。
- `DesktopSettings.syncActive()`: `settingsEls.dialog.contains(document.activeElement)` でアクティブかどうかを決める（明滅中は上書きしない）。
- 呼び出しは `desktop.js` の `scheduleActiveTitlebarSync()`（rAF で 1 フレームに 1 回へまとめる）に一本化し、`document` の `focusin`/`focusout`、`window` の `blur`/`focus`、iframe の `load`、`#view-desktop` への `pointerdown`、およびウィンドウ/ダイアログそれぞれの開く・閉じる・最小化・復元の操作から呼ぶ。後者はモジュール間の相互 import を避けるため、`DesktopWindow.init()`/`DesktopSettings.init()` に渡すコールバックとして注入した。

### 初期状態（起動時）の扱い

「実フォーカスから毎回導出する」方式をそのまま起動直後にも適用すると、ページを開いた直後はまだ何にもフォーカスが無い（`document.activeElement === document.body`）ため、ウィンドウは非アクティブと判定されてしまう。これは実機の Win95 が「起動した時点で開いているウィンドウはアクティブ」であるのと食い違い、既定のスクリーンショット（`docs/assets/dashboard-desktop.png`）の見た目も変わってしまう。

そこで「起動時はアクティブ」を明示的な既定として選び、一度も実フォーカスが動いていない間はこの導出自体を呼ばないようにした（`hasHadRealFocus` フラグ。`document.activeElement` が `body`/`html` 以外になった瞬間に一度だけ立ち、以後は常に導出する）。HTML の初期状態には `.is-inactive` が付いていないので、導出を呼ばなければ自動的に「アクティブ」に見える。

### 追加で見つかったバグ（ユーザー報告、同ラウンド内）

ツールバーの「更新」ボタン（`#desk-reload`）を押す（クリック/キーボードのどちらでも）とウィンドウが非アクティブになる、という報告が追加であった。原因は `setBusy()` がクリック直後にボタンを `disabled = true` にすることで、そのボタン自身にあった実フォーカスが強制的に `body` へ落ちるため（`disabled` にした要素は同期的にフォーカスを失う仕様）。`syncActive()` を修正しても、実フォーカスが本当に `body` に落ちてしまえば正しく「非アクティブ」と判定してしまう——これは syncActive 側のバグではなく、フォーカスの落ち先自体の問題だった。

修正: `#desk-reload` のクリックハンドラで `this.load(...)` を呼んだ直後に `DesktopWindow.focusWindow()`（`#desk-window` へ `.focus()`）を呼び、ウィンドウの中へフォーカスを戻す。

ついでに監査すると、メニューバー・ツールバーの装飾部分・アドレス欄・ステータスバーなど、ウィンドウ内のフォーカス不可能なクロムをクリックしてもブラウザは自分からフォーカスを動かさない（クリック前から何もウィンドウにフォーカスが無かった場合、クリックしてもウィンドウはアクティブにならない）ことにも気づいた。Win95 の実機では、ウィンドウのどこをクリックしてもそのウィンドウがアクティブになる。`#desk-window` に `pointerdown` を張り、クリック対象が実際にフォーカスを受け取る要素（`button`/`input`/`[tabindex]`）でなければ `#desk-window` 自身を明示的に `.focus()` する形で揃えた。

タスクバーのタスクボタンから最小化中のウィンドウを復元するクリックも、ウィンドウへフォーカスを戻す処理が無かった（最小化ボタンからの最小化・アイコンからのオープンには元々あった）ので、同様に `winEls.win.focus()` を足した。

### 検証（f3 ラウンド、すべて実際のマウス/キーボード操作）

- iframe 内のリンクへ実際に Tab でフォーカスを移す → ウィンドウのタイトルバーはアクティブのまま（`inactive: false`）。
- ウィンドウがアクティブな状態から「コントロール パネル」アイコンをダブルクリック／Enter のどちらで開いても、ウィンドウは非アクティブ・ダイアログはアクティブになる。

- 実際のマウスでデスクトップの何もない場所をクリック → ウィンドウは非アクティブになる（`document.activeElement` が `body` になることを確認。これは意図通りの挙動として維持）。
- 実際のマウスでウィンドウのタイトルバー（ボタン以外の余白）をクリック → `#desk-window` にフォーカスが移りアクティブになる。
- 「更新」ボタンをマウスクリック／キーボード（Tab→Enter）のどちらで押しても、押している間・押した直後ともウィンドウはアクティブのまま。
- ステータスバー・メニューバー・アドレス欄のクリックでも同様にウィンドウがアクティブになる。
- 最小化 → タスクボタンのみアクティブ表示、ウィンドウは非表示。タスクボタンをクリックして復元 → ウィンドウへフォーカスが戻りアクティブになる。

- ページを完全に再起動して `#/desktop` を開いた直後（何も操作していない状態）で、ウィンドウのタイトルバーが既定でアクティブ表示になっていることを確認（`document.activeElement` は `BODY` のまま）。
- `cargo fmt --check` / `cargo clippy -j 4 --all-targets -- -D warnings` / `cargo test -j 4 --workspace` を実行。475 passed, 16 ignored、失敗 0（既知のフレーキーテストも今回は発生しなかった）。

## 追記: コントロール パネルの「削除」「適用」が自分を disabled にしてダイアログを非アクティブにするバグの修正（同日、f4 ラウンド。9794a15 の後の追加修正）

ユーザー報告: 「コントロール パネル」ダイアログで「削除」または「適用」を押すと、ダイアログのタイトルバーが非アクティブになる。両ボタンとも実行後に自分自身を `disabled` にし、それがフォーカスを `body` へ落とすため（`syncImagePanel()` の既存の保険は「削除」はカバーしていたはずだが実地確認が漏れており、「適用」側には保険が一切無かった）。

### 実地確認したこと

- 「適用」を実際にマウスクリックすると再現した（`dialogInactive: true`, `document.activeElement` は `BODY`）。「適用」には保険が無いので当然。
- 「削除」は実は既存の `syncImagePanel()` の保険で既に直っていた（マウス・キーボードとも `dialogInactive: false` を確認）。ただし保険の実装がダイアログ「コンテナ」へ戻すだけで、コーディネーターが求める「削除 → 参照... へ」という、より Win95 らしい具体的な戻し先にはなっていなかった。
- 「既定の色に戻す」は自分自身を `disabled` にするコードが無く、そもそも対象外（実地確認のみ、修正不要）。

### 修正

- `removeImage()`：`syncImagePanel()`（「削除」「表示方法」を disable する）の前後でダイアログがフォーカスを含んでいたかを比較し、含まなくなっていれば「参照...」（`browseBtn`）へフォーカスする。
- `applyOnly()`：`tryApply()`（成功すると「適用」を disable する。失敗時は disable されないのでこの分岐に入らない）の前後で同様に比較し、含まなくなっていれば OK（`okBtn`）へフォーカスする。
- 汎用の保険として、`#desk-dialog-control-panel` に `focusout` リスナーを追加した。`ev.target.disabled` を見て、実際に無効化されたことが原因で外へ出た場合だけ（`requestAnimationFrame` で 1 拍置いてから）ダイアログへ戻す。「無効化が原因かどうか」を見ているので、無効化を伴わない普通の blur（後述のオーバーレイクリックなど）では発火しない。
- 同じ理由で `desktop-window.js` の `#desk-window` にも同じ形の `focusout` の保険を足した（コーディネーターの依頼どおり）。

### 実装中に見つけて直した自分のバグ: `activeElement === body` を直接ポーリングする版の保険は誤発火する

最初は `DesktopSettings.syncActive()` の中に「ダイアログが開いていてフラッシュ中でなく、`document.activeElement` が `body`/`html` ならダイアログへ `.focus()` する」という汎用の保険を書いたが、これは誤り。オーバーレイ（透明でクリックを塞ぐ、外側クリックでフラッシュさせるための要素）はフォーカス不可能なので、外側をクリックすると実フォーカスはブラウザの既定動作で **必ず** 一旦 `body` に落ちる（無効化とは無関係に、ただの「フォーカス不可能な要素をクリックした」結果）。`mousedown` 直後・`flashTitlebar()` が呼ばれる前のタイミングで `document.activeElement` を確認すると実際に `body` になっており、この時点で `syncActive()` のポーリング版がまだ動いていて（`rAF` 経由で数十ms 後に発火する）、フラッシュが始まる前にダイアログへフォーカスを奪い取ってしまうことを実機で確認した。これは「オーバーレイクリックによるものは除く」という要求に反する。

`ev.target.disabled` を見る版（`focusout` イベントの対象が実際に `disabled` になっているかどうか）に置き換えて解決した。オーバーレイクリックでは blur した要素（例: 「既定の色に戻す」ボタン）が `disabled` になるわけではないので、この版では発火しない。

### 実装中に見つけた関連の未解決状態: フラッシュ後にフォーカスが `body` のまま残っていた

上のポーリング版を `ev.target.disabled` 版に直した後、オーバーレイクリック自体は正しく無視されるようになったが、別の実地確認で「フラッシュが終わった後も実フォーカスは `body` のまま」であることが分かった。これ自体は見た目には現れない（`stopFlash()` が明示的に `.is-inactive` を外すため）が、フラッシュの後に何か別のイベント（例えば `window` の `blur`/`focus`。あるいは他画面から Alt+Tab で戻ってきたときなど）が `scheduleActiveTitlebarSync()` を再度呼ぶと、そのとき初めて `DesktopSettings.syncActive()` が「実フォーカスはダイアログの外（`body`）にある」と正しく（？）判定し、タイトルバーが理由もなく非アクティブに変わってしまうことを実機で確認した（`window.dispatchEvent(new Event('blur'))` → `focus` で再現）。

「開いている間は常にアクティブに見える」という前提が、フラッシュ後は実は成り立っていなかった（たまたま次の再同期が起きるまで気づかないだけ）ということなので、`stopFlash()` の末尾で、クラスを戻すのと同時に、フォーカスがダイアログの外に出ていればダイアログ自身へ戻すようにした。これでフラッシュが終わった時点で実フォーカスも見た目と一致し、後から別のイベントで再同期されても崩れなくなった（`window` の `blur`/`focus` を発火させて確認済み）。
