# コード全体のレビューとセキュリティの強化

コード全体を、ダッシュボード・IPFS と Kubo・Nostr と設定・サービスとパッケージングの 4 領域に分けて見直した。見たのは、膨れたファイル・重複・複雑または非効率な実装・過剰なコメントと、セキュリティ上の問題。直したあとに、前の経緯を知らない別のレビューで評価し直すことを 4 回繰り返した。4 回目で CRITICAL・HIGH の指摘がなくなったので終えた。

## 決めたこと

- 公開した版を MFS から消すのは、署名に失敗したとき（まだ何も送っていないとき）だけにする。一度は、どの relay にも受理されないときや、ダッシュボードでの公開が打ち切られたときも消すようにした。ところが送信の途中で打ち切られた場合や、応答を待ち切れなかった relay にもイベントが届いている場合に、告知した版を消してしまう。そこで、署名できた時点で版を残すことにした。
- 起動時の突き合わせで「中身が欠けている」とするのは、Kubo がブロックを手元に見つけられないと答えたとき（`ipld: could not find`）だけにする。それ以外の `dag/stat` の失敗（タイムアウトなど）で版を state から落とすと、次の sweep で MFS からも消え、取り直せない古い版を失う。
- 読めない `kubo.pid` は、警告を出して「記録された Kubo は無い」とみなして続ける。止めると、サービスマネージャの下で起動を繰り返す。本当に Kubo が残っていれば、リポジトリのロックで止まって既存のヒントが出る。
- `swing service install --system` は、実行ファイル・設定・作業ディレクトリ・Kubo のバイナリと、その親ディレクトリが root かサービスのユーザーのものであり、グループや他のユーザーが書き込めないことを確かめる。root で動かすときは `--allow-root` を求める。root 所有でグループが書き込める上位のディレクトリ（Debian の `root:staff 2775` の `/usr/local`）は、管理者が意図して任せたものとして受け入れる。バイナリのすぐ上のディレクトリには、この例外を当てない。
- 自分のレプリカ報告は relay ごとにページに分けて全部読む。1 ページより多くの報告が同じ秒に並ぶと読み進められなくなるので、1 回に送る報告には 1 秒ずつ違う `created_at` を付ける。

## 変えたもの

- ダッシュボード
  - `/api/login-code` と `/api/token/rotate` には、ブラウザのセッションではなくトークンを求める。
  - アップロードの本体を書く前に公開のロックを取る。一時ディレクトリの名前は乱数にして、再帰せずに作る。
  - ゲートウェイは、クライアントの `Cookie` と `Authorization` を上流に渡さない。
  - ミラーの追加と削除を 1 つずつ処理し、同時に来た変更が消えないようにした。
  - `api.rs` を `error.rs`・`publish.rs` に分け、公開の結果の組み立てと静的ファイルの表をまとめた。
- IPFS と Kubo
  - 取得の前に、ルートのブロックだけでディレクトリかどうかを確かめる。取得量の上限は、アカウントとノードの残りの容量までに抑える。
  - 公開するファイルは、一覧にしたものとすり替わっていないことを確かめてから開く（unix）。シンボリックリンクで同じディレクトリに何度も入る構成は断る。
  - `PATH` の相対パスにある `ipfs` は使わない。Kubo には `SWING_` の秘密の環境変数を渡さない。`kubo.pid` は原子的に書く。
  - Kubo の設定は 1 回の JSON の書き換えで当てる。
  - `kubo.rs` を `src/kubo/` に分けた。
  - MFS への書き込みの間は state のロックを持たない。フォローを外したアカウントの再試行の記録は消す。
- Nostr と設定
  - 秘密鍵は `Zeroizing` で持ち、`expose_secret()` からしか読めないようにした。
  - 秘密鍵を含む設定ファイルを他人が読めるときは警告する。relay の URL とミラー対象リストは、設定を組み立てるときに検証する。
  - 一部のチャンクの取得に失敗しても、取れた分は使う。
  - 大きなテストを別のファイルに移し、`nostr/client.rs` と設定の一覧を分けた。
- サービス・パッケージング・CI
  - `install.sh` は HTTPS 以外でダウンロードせず、グループが書き込めるディレクトリには入れない。
  - Windows では `schtasks.exe` と `rundll32.exe` をシステムディレクトリから呼び、`schtasks` のすべての呼び出しに時間制限を付けた。タスクの XML は宣言どおり UTF-16LE で書く。
  - compose の mirror はすべての capability を落とす。CI の checkout は認証情報を残さず、リリースのビルドはキャッシュを使わない。

## 検証したこと

- `cargo fmt`・`cargo clippy -D warnings`・`cargo test --workspace`・Windows 向けの `cargo xwin clippy` が通る。
- 本物の Kubo 0.43.1 で、`#[ignore]` の統合テスト（`kubo_integration`・`mfs_kubo_integration`・`kubo::` のプロセス管理）が通る。Kubo のブロックが欠けているときの応答が、欠けているものとして判定されることも確かめた。
- `packaging/linux/test-install.sh` を一般ユーザーと root（Debian のコンテナ）で実行した。
- デモ環境（`docker/demo/demo.sh up --seed`）では、次を確かめた。
  - サンプルの公開・ミラーの追加・保存・レプリカ報告。
  - ダッシュボードからのアップロード公開。
  - 中身が変わらないときに追加した版を取り下げること。
  - トークンなしの `/api/login-code` を断ること。

## 残したもの

- リリースへの署名（`SHA256SUMS` の署名や provenance）。仕組みを選ぶ必要がある。
- カレントディレクトリの `swing.toml` を自動で読み、その `[kubo].binary` を実行できること。読む順は仕様として文書にあるので、変えるかどうかは別に決める。
- root 所有でグループが書き込めるディレクトリの扱いを、バイナリのすぐ上のディレクトリにも広げるかどうか。Debian で `/usr/local/bin` も `root:staff 2775` の環境では、いまは `--prefix /usr/local` での導入と `--system` の登録を断る。
- systemd ユニットの `ProtectSystem=strict` などの追加の制限。実環境で確かめてから入れる。
