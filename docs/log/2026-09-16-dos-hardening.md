# 2026-09-16 DoS 耐性の強化（実サイズ判定・取得上限・並行処理・アカウント上限・NIP-05 キャッシュ）

## 目的

レビューで挙がった、フォロー中の相手（鍵を盗まれた人やミスした人も含む）や relay による DoS を抑える。

| # | 問題 | 対応 |
|---|---|---|
| A | `size` タグを小さく偽ると、pin 後に実サイズを確認しないためディスクが埋まる | 実サイズで判定する |
| B | 取得できない CID があると、直列処理で最大 1 時間止まり、他サイトの処理が進まない | 既定タイムアウトの短縮、無通信タイムアウト、並行処理 |
| C | 1 人が `d` を変えて大量のサイトを出すと、容量をいくらでも使える | `max_per_account` |
| D | `size` タグが無いと、上限チェックの前に全部ダウンロードされる | 取得中にバイト数を数えて打ち切る |
| E | 変わっていないサイトも poll ごとに NIP-05 を再検証し、遅いドメインで 1 件 10 秒食う | 結果のキャッシュ、事前判定で skip するものは検証しない |
| F | relay が大量のイベントを返せる | 低懸念として todo に積んだ |

## 決めたこと

| 決定 | 理由 |
|---|---|
| 取得を `pin/add` ではなく `dag/export` のストリームで行い、受信バイト数で打ち切る | Kubo の `pin/add` の進捗はブロック数しか返さずバイト数で止められない。`dag/stat` や `files/stat` の事前確認は、前者は全ブロックを取得してしまい、後者はルートノードの自己申告（Tsize）で偽れる。CAR の受信量ならブロックの実データなので偽れない |
| 取得後の `pin/add` と `dag/stat` に `offline=true` を付ける | `dag/export` がストリームの途中で失敗しても HTTP としては正常終了に見える（エラーは trailer）。その後の pin がネットワークから残りを取ると上限を回避されるので、ローカルにあるものだけで pin させる。online の daemon でも即エラーになることを確認した |
| 実サイズは `dag/stat` の `TotalSize` を記録する | CAR のバイト数は各ブロックのヘッダー分だけ大きい。publish が `size` タグに入れる `files/stat` の `CumulativeSize` と同じ尺度にする |
| 取得の上限は `max_update_size`・`max_per_site`・`max_per_account` の最小値。残りの全体容量は使わない | 全体容量はほかのタスクの確定で変わるので、取得後の判定に任せる。取得中の一時的な超過は最大 `concurrency` × 上限 |
| `size` タグは事前判定にだけ使う | 正直な作者の巨大な更新を、ダウンロードせずに skip できる |
| `SWING_PIN_TIMEOUT` の既定を 1 時間から 15 分に | 個人の静的サイトなら十分。無通信タイムアウトがあるので、取れない CID で全体タイムアウトまで待つことはまず無い |
| `SWING_FETCH_IDLE_TIMEOUT`（既定 2 分）を追加 | 取れない CID は最初のブロックが来ないので、ここで早く諦められる。`dag/export` は最初のブロックまでヘッダーも返さないので、送信にも同じタイムアウトをかける |
| 並行数は `[agent].concurrency`（既定 4）のセマフォ | 取れない CID があっても他のサイトが進む |
| 同じサイトは同時に 1 タスク。待機は最新 1 件だけ | 同じサイトの版を並行に判定すると、stale や evict の判定が崩れる。途中の版は最新版が来れば不要 |
| 判定から state 保存までを state のロックの中で直列に行う | 並行に取得しても、容量の判定は確定した pin を必ず見る。`pin/add` は offline で速いので、ロックを長く持たない |
| 解放（unpin）は state 上で他に参照が無い CID だけ | 別のサイトと同じ CID を出して reject させ、相手のサイトの pin を外す攻撃ができた |
| evict した版は、`pin/rm` に失敗しても state から消す | 以前は失敗した版を state に残していたが、再試行もされず容量だけ数え続けていた。起動時の突き合わせで報告される |
| Follow Set の更新を unfollow の unpin より先に反映し、取得後にもう一度フォロー中か確認する | 取得中に unfollow されたとき、unfollow の後で pin されて残るのを防ぐ |
| unfollow で、pin されていないサイトの `verifications` も消す | 以前は `sites` にあるキーだけ消していた |
| `max_per_account` の既定は 20GB | `max_per_site`（10GB）より大きくないと、サイトを複数持つ人が保存されない |
| NIP-05 のキャッシュは `state.verifications` の `checked_at` を使う。既定 1 日、`error` は 15 分とのうち短い方 | 新しい保存場所が要らず、再起動しても効く。一時的な失敗が 1 日続かないように error は短くする |
| 事前判定を NIP-05 検証より先にする | 変わっていないサイト（`duplicate_cid` / `stale`）は検証しない。そのため、そうしたサイトの検証結果は更新されなくなる |
| compose の Kubo を `--enable-gc` で起動し、README で `Datastore.StorageMax` の設定を勧める | 打ち切った取得や解放したデータは GC でしか消えない |
| 起動時の Follow Set 取得を、`interval` の最初の tick に任せる | 以前はループの前に 1 回呼び、直後の最初の tick でもう 1 回呼んでいた |

## 見送ったこと

- 失敗した CID の指数バックオフ、1 pubkey あたりのサイト数上限、relay から取得する件数の上限、手動 pin の保護は `todo.md` に積んだ。
- 取得を打ち切ったり解放したりしたブロックは、GC が走るまで残る。GC の条件は Kubo の設定次第。
- `dag/export` は DAG を順にたどるので、ブロック数の多いサイトでは `pin/add` より遅い可能性がある。

## 検証

- `cargo fmt` / `cargo clippy --all-targets -- -D warnings` / `cargo test`（ユニットテスト 120 件）。
- agent のテストに追加したもの: 取得中の打ち切り、実サイズでの再判定、事前判定で取得しないこと、アカウント上限、共有 CID を解放しないこと、取得中の unfollow、同じサイトの合流、NIP-05 キャッシュ（通常と error）、skip 時に検証しないこと。
- 取得中の unfollow のテストは、取得後のフォロー確認を外すと失敗することを確かめた。
- ローカルの Kubo 0.43.1（`IPFS_PROFILE=test`、公開ネットワークに接続しない）で統合テスト 4 件を実行した。`dag/export` の打ち切り、`dag/stat`、存在しない CID の取得が無通信タイムアウト（2 秒）で終わること、`offline=true` の pin が即失敗することを確認した。
- 同じ Kubo で、`offline=true` を付けない `pin/add` は存在しない CID で 5 秒以上返らないこと、`dag/export` は最初のブロックまでヘッダーを返さないことを curl で確認した。
