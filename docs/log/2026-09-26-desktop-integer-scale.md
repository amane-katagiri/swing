# Desktop 画面の表示倍率を整数倍に揃える

## 背景

ブラウザのズームや OS の表示スケールが 125%・150% などの整数倍でないと、Desktop 画面のドット絵フォント（PixelMplus12、アンチエイリアス無し）と 1px のベベルで、デバイスピクセルの幅が 1 と 2 に不揃いになり、文字と枠線が歪んでいた。

## 決めたこと

| 決定 | 理由 |
|---|---|
| `#view-desktop` に CSS `zoom = n / devicePixelRatio`（`n = max(1, floor(devicePixelRatio))`）をかけ、1 CSS px を常に `n` デバイスピクセルにする | ドット絵は整数倍でしか崩れずに描けない。フォントの設定だけでは直らない |
| 丸めは切り捨て（200% 未満は 1 倍） | 画面が勝手に大きくならないようにするため。四捨五入や切り上げにすると、150% や 110% で 2 倍に跳ね、スクリーンに収まる範囲が半分になる。ユーザーの判断でピクセル優先の方式だけにし、倍率どおりに描く切り替えは入れていない |
| 倍率の変化は `resolution` メディアクエリの `change` と `resize` の両方で拾う | ズームではビューポートの大きさも変わるので `resize` も飛ぶ。検証に使った CDP の deviceScaleFactor エミュレーションでは、メディアクエリの `change` が 1 回遅れて届くことがあった |
| iframe（リンク集ページ）は、中の `devicePixelRatio` が整数倍率になっていなければ、iframe 要素で親の `zoom` を打ち消して iframe の文書のルートに `zoom` をかける。なっていれば何もしない | Chromium は親の `zoom` を iframe の中にそのまま伝え、中の文字もそろう。Firefox も描画には伝えるが、中の `devicePixelRatio` は補正前の値のまま返り、160〜190% などで中の文字がにじんだり大きさが揺れたりした。そのまま iframe の文書に `zoom` を足すと二重にかかって小さくなるので、iframe 要素で打ち消してから足す。WebKit は `devicePixelRatio` は整数倍率を返すが、iframe の中の文書の画面サイズ（ICB。`100%`・`vh` の基準と背景を塗る範囲）を親の `zoom` の分だけ縮めてしまい、中身が枠の 8 割にしか広がらなかった。打ち消す形なら WebKit も埋まる。打ち消す形は Chromium では逆に 110%・150% でにじんだため、ブラウザ名ではなく、中の `devicePixelRatio` が整数倍率か、`documentElement.clientHeight` が `innerHeight` から縮んでいるかで分ける（高さで見るのは、縦スクロールバーで幅が変わるのを避けるため） |
| `#view-desktop` と iframe の左上を、`left`/`top` を 1 デバイスピクセル未満ずらしてデバイスピクセルの境目に合わせる | 110% ではサイドバーの幅 208px が 228.8 デバイスピクセルになり、整数倍にしても全体がにじんでいた。Firefox では iframe より上の文字の高さも補正後の値で丸められ、iframe の左上が半端になる |
| iframe を `transform: scale()` で縮める方式は採らない | Firefox では iframe を描いてから画像として縮めるので、全倍率でにじんだ |
| SE ロゴの E を、S との隙間を切り欠いた塗りの図形にして `mask` をやめる | Firefox では外部ファイル（`desktop-icons.svg`）の `<symbol>` に付けた `mask` が CSS `zoom` の内側でずれ、E の大部分が消えた。同じ SVG を文書内に直接書いた場合は崩れない。切り欠きの形は、元の mask と同じ幅 10.5 の S のストロークを E から引いて計算した |
| ポインタ座標・`getBoundingClientRect()` は `toDeskPx()` で換算し、スクリーンの大きさは `clientWidth`/`clientHeight` から取る | `zoom` の内側では、`style.left` などは補正前の値、`getBoundingClientRect()` やイベントの座標は補正後の値になるため |

## 検証

デモ環境の `#/desktop` を、Chromium の deviceScaleFactor 1・1.25・1.5・2・2.5・3 で表示して確かめた。

- 補正値（`zoom`）と iframe の中の `devicePixelRatio` が、どの倍率でも想定どおり（1.25 と 1.5 は 1 倍、2.5 は 2 倍）
- 150% と 125% で、補正の前後のスクリーンショットを拡大して比べた。補正前は文字の線幅が不揃いだったが、補正後はそろっていた（iframe の中の文字も同じ）
- 150% で、ウィンドウのドラッグ、最大化から戻しながらのドラッグ（カーソルはタイトルバーの同じ割合の位置に残る）、ダイアログのドラッグ、コンボボックスのリストの位置が、ポインタの動きと一致した

- Chromium の 1.1・1.25・1.5・1.75・2.5 倍で、`#view-desktop` と iframe の左上がデバイスピクセルの境目（ずれは 0.03 デバイスピクセル未満）に来た
- Firefox（Playwright）の 1・1.1・1.25・1.5・1.7・1.9・2・2.5 倍で、左上の位置・SE ロゴ（デスクトップアイコン・タイトルバー）・iframe の打ち消しの有無（整数倍率では打ち消さない）を確かめた。Linux の headless Firefox は文字をグレースケールでアンチエイリアスするので、iframe の中のにじみは Windows の Firefox で目で見て判断した
- WebKit（Playwright の Linux 版）の 1・1.25・1.5・1.7・2 倍で、iframe が枠いっぱいに描かれることを確かめた。ただし文字は、`zoom` の内側の文字サイズが整数 px に丸められるため 1.25・1.75 倍などで少し大きく描かれ（175% で 12.25 デバイスピクセル）、150% では位置が半ピクセルずれて、親のデスクトップもリンク集ページもぶれた。Safari の実機では確かめていない（`docs/todo.md` に積んだ）
- Firefox では `zoom` の内側の `border` の幅が指定値によらず同じ幅に丸められ（1px・2px・0.5px が同じ幅になる）、枠線のあるリンク集ページでは中の要素の位置が 1 デバイスピクセル未満ずれる。差し替えたページも同じなので、スクリプトでは直していない
