# 署名アプリとのペアリングの相互運用

前日のセキュリティレビューでペアリング（`nostrconnect://`）を自前で実装し直し、secret を返す接続の応答だけを受け入れるようにした。紹介している署名アプリの Amber と Clave がこれでつながるかを、両アプリのソースを読んで確かめた。

## 調べたこと

- Amber（v6.6.6）: 接続の応答に URI の secret を返し（secret が無いときだけ `ack`）、NIP-44 で暗号化して URI の relay に送る。以降の応答も接続ごとに作る同じ鍵から来る。接続の応答を送る前に受信の購読を張るので、直後の要求も取りこぼさない。
- Clave（iOS）: 単一アカウントでは secret を返し、NIP-44 で暗号化する。ただし接続の応答を送った直後に relay の購読を張り直すので、その間に届いた要求（kind 24133 は relay に残らない）は拾われない。SWING は接続の応答を受けてすぐ `get_public_key` を 1 回だけ送っていたので、それが失われると 60 秒待って失敗しうる。Clave の設計文書もクライアントに `get_public_key` の再送を求めている。
- 両アプリとも、断ったときは `result` を空にして `error` に理由を入れて返す。SWING は `result` を先に解釈して失敗し、「応答を読めなかった」としか出していなかった。
- 前の nostr-connect も通信は NIP-44 だけだったので、暗号化の方式は書き直しの前後で変わっていない。

## 変えたこと

- `get_public_key`（と `ping`）は、応答が来るまで 5 秒ごとに新しい id で送り直し、送ったどの id への応答でも受け入れる。待ち時間の上限は延ばさない。同じ id で送り直さないのは、同じイベントを relay が重複として配らない・署名アプリが処理済みの id を無視する、のどちらも起こりうるため。`sign_event` は副作用があるので送り直さない。
- 応答は `error` を先に見て、空でなければ「the signer app refused the request: <理由>」にする。理由は表示用に制御文字を除いて 500 文字までにする。`result` の解釈はその後。

毎回承認を求める設定の署名アプリでは、再送のぶん承認の確認が複数出ることがある。

## 検証

- 最初の `get_public_key` を無視する偽の署名アプリで、ペアリングが再送で約 5 秒後に通ることをテストで確かめた。断りの理由が接続・署名の両方で表示されることもテストした。

## 実機での確認

`swing signer pair`（relay は `wss://yabu.me` と、もう 1 つ公開の relay）で確かめた。

- Amber: ペアリングと試し署名が通った。試し署名をアプリで拒否すると「the signer app refused the request: user rejected」と理由が出て、ペアリング自体は保存された。
- Clave: ペアリングと試し署名が通った。試し署名を拒否したときも Amber と同じく理由（`user rejected`）が出た。別のアカウントで保存済みのときは、Clave の公開鍵を受け取ったうえで「別のアカウントには切り替えない」エラーで止まった（接続と `get_public_key` の応答は届いている）。
- `swing signer pair` の既定の relay（`wss://relay.primal.net`）はこのとき接続できず（IPv4 で 502、IPv6 でタイムアウト）、`--relay` で別の relay を指定した。既定が 1 つだけなので、そこが落ちているとペアリングがすぐ失敗する。
