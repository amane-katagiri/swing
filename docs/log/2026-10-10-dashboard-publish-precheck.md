# ダッシュボードで公開する前に確認の結果を見せる

## 背景

ダッシュボードの公開画面では、ドットファイル・サイズ・リンクの確認の結果は、フォルダを全部アップロードして publish の処理が走った後にしか分からなかった。`require` で止まる場合も、大きなサイトを送り終えてから止まる。増えたファイルの確認（previous-files）と同じく、送る前に結果を見せて、このまま公開するかを選べるようにする。

## 決めたこと

| 決定 | 理由 |
|---|---|
| `links::scan` を、全ファイルのパスと大きさの一覧と「パスから中身を返す関数」から判定する `links::evaluate` に分け、`swing publish`・upload（`SiteListing` から読む）と事前の確認（ブラウザから受け取る）の両方がそれを使う | 判定を 1 つにして、事前の確認と本番の判定が食い違わないようにする |
| 事前の確認の API は `POST /api/publish/check`。全ファイルのパスと大きさを JSON で、中身はリンクの確認が読むファイル（拡張子と 4 MiB 上限は今と同じ）だけを送る | 画像や動画の中身まで送ると、確認のためにサイトを 2 回アップロードすることになる。ドットファイルとサイズはパスと大きさだけで判定できる |
| パスの検証は upload と同じ規則を `upload::PathRules` として共有し、大きさの合計が `[dashboard].max_upload` を超えたら upload と同じく 413 | 事前の確認で通ったのに upload で 400・413 になる食い違いを避ける |
| 何も保存せず、Kubo にも relay にも触らない。多重実行の排他（409）も付けない | 読むだけの判定で、publish の処理と取り合うものが無い |
| ボディの上限とタイムアウトは upload と同じルートの層に置く | HTML・CSS・JavaScript の中身だけでも、既定の 2 MB の上限を超えうる |
| 応答は upload の `checks` と同じ形と、`require` で止まる理由（`abort`） | 画面は結果のパネルと同じ `addCheckRows` で出せる |
| 画面では previous-files と同時に呼び、確認で何か見つかったか増えたファイルがあれば、同じ `#publish-confirm` のパネルに上下に並べる（確認の結果が上） | 確かめる場所を 1 つにする。止まる理由のほうが重いので上に置く |
| `require` で止まる結果なら公開のボタンを出さず、`#publish-status` に止まる理由を出す（文言は結果の 422 と同じ案内を使う） | 押しても upload で止まるだけなので、押せるようにしない |
| 事前の確認はあくまで案内で、upload は今までどおり自分で判定する | ブラウザから送られた一覧や中身は、実際にアップロードされるものと同じとは限らない |
| ブラウザ側に、読むファイルの拡張子と 4 MiB を定数で持つ | 送る中身を選ぶため。サーバーは対象外の中身を 400 で断るので、ずれたら気づける |
| 動作性の確認の行は、種別ごとに説明の 1 行と、参照を 1 件 1 項目のリストで並べる（結果パネルと公開前の確認パネルで共通）。リストには増えたファイルの一覧と同じ `.swing-file-list` を使い、新しいクラスは足さない | `, ` でつなぐと参照の境目が見にくいと利用者から指摘があった。`.swing-file-list` は等幅・折り返し・余白トークンの上下の余白を持ち、種別ごとの件数は表示の上限（5 件）で収まるので高さの制限にも当たらない |
| 動作性の確認の参照元の並びを、増えたファイルの一覧と同じ（最上位のファイルが先、続けてフォルダごと、同じファイルの中は出てきた順）にし、Rust 側で並べてから種別ごとの先頭 5 件を切り出す。比べ方は CLI の増えたファイルの一覧と同じバイト順で、画面の増えたファイルの一覧（UTF-16 のコード単位順）と食い違いうるのは U+E000 以降と U+10000 以降の文字が混ざったときだけなので、文書に書くにとどめた | 利用者から、増えたファイルと並びをそろえてほしいと指示があった。並べる場所を 1 つにすれば、CLI・公開前の確認・公開後の結果が同じ順になる |

## 作ったもの

- `src/publish/links.rs`: `evaluate`（一覧と読む関数から判定）・`scanned`（読むファイルか）。`scan` は `evaluate` を使う。
- `src/ipfs/site.rs`: `SiteFile::path` が一覧の寿命の `&str` を返すようにした（パスから `SiteFile` を引く表を作るため）。
- `src/dashboard/precheck.rs`（新規）: `POST /api/publish/check`。
- `src/dashboard/upload.rs`: `PathRules`（パスの検証・重複・ファイルとディレクトリの衝突）、`read_field_bytes`。テスト用の multipart の組み立てを `test_support.rs` に移した。
- `src/dashboard/publish.rs`: `validate_site_and_url`・`resolve_modes`（upload と check で共有）。
- `web/publish.js`・`web/index.html`・`web/style.css`・`web/i18n.js`: 事前の確認の呼び出し、確認のパネル（`#publish-confirm-checks`・`#publish-confirm-new`）、文言（英語・日本語）。確認のパネルの `.swing-result-grid` の下の余白を `--swing-space-4` にした。
- 文書: `docs/architecture/dashboard/http-api/publish.md`（`POST /api/publish/check`）・`http-api.md`・`dashboard.md`・`views/publish.md`・`architecture/publish.md`・`publish/links.md`・`docs/guide/publish.md`。

## 検証

- `cargo fmt --all`・`cargo clippy --workspace --all-targets -- -D warnings`・`cargo test --workspace` が通る。API のテスト: 確認の結果（ドットファイル・サイズ・リンク・4 MiB を超えるファイルを読まなかった数・止まる理由）、モードの指定と既定値、`off` なら読まないこと、パスの検証（`..`・`/` 始まり・空のセグメント・大文字小文字の重複・ファイルとディレクトリの衝突・予約デバイス名・空の一覧・形の違う JSON）、一覧に無い中身・読まないファイルの中身の拒否、上限を超えたときの 413、`site`・`url`・モードの不正、状態ディレクトリに何も書かないこと。
- デモ環境で、日本語の表示にして、問題のある見本サイトを `warn` で選ぶと確認のパネルに結果（修正ガイドのリンクを含む）と増えたファイルが上下に並び、「このまま公開」「キャンセル」が出た。`require` では公開のボタンが出ず、`#publish-status` に止まる理由が出た。「このまま公開」で公開すると、結果のパネルに同じ確認の行が出た。問題の無い見本サイトは、初回は増えたファイルだけのパネル、同じ内容での 2 回目はパネルを出さずにそのままアップロードされた。パネルの中の余白と、前後の要素との余白も確かめた。
- 見本サイトの説明にある期待（止まるもの・警告だけのもの）は、CLI でもダッシュボードでもすべて検出された。説明に無い検出は、`http://` のスクリプトが「ほかのホストからの読み込み」にも出ることだけで、仕様どおり。
