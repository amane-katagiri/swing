# 2026-09-27 README に運用の目安を書く

[間欠運用と通信量](2026-09-23-intermittent-operation-and-traffic-limits.md) で保留にしていた「常時起動しない場合に何が起きるか」を README に書いた。あわせて、想定している使い方・必要なスペック・リソースと通信量の見積もりをまとめた。

## 決めたこと

- 置き場所は README。protocol ではなく利用者が導入前に知りたい運用の話で、architecture は「今のコード」の記述なので合わない。「どれくらい保存されるか」の後に `## 動かし方の目安` として置き、「必要なもの」から 1 行でリンクした。
- 想定する使い方は「常時起動のサーバでも普段使いの PC でもよい。普段使いなら使っている間だけ起動すればよい」と明記した。常時起動が要るのは自分ではなく相互ミラーの網のうち誰か、という 09-23 の整理をそのまま結論にした。
- 報告が切れない目安は「1〜2 日に 1 回、しばらく起動する」。`report_ttl` 既定 `3d`、出し直しは半分の 1.5 日ごと、受信側は 7 日より古い報告を数えない、の 3 つから。
- Kubo のリソースと通信量は公開 IPFS で実測しなかった（測る側のノードの IP と Peer ID を公開 DHT に載せることになるため）。根拠のない数字は書かず、何もしなくても通信があることと、利用者が自分で確かめる手段として `ipfs stats bw` を案内した。メモリも Kubo が大半を使い接続数で増えることだけ書き、必要な空き容量の目安は出していない。実測は `docs/todo.md` に足した。
- 通信量を抑えたい場合は、今は SWING ごと止めるしかないと書いた。compose では `mirror` を止めても `ipfs` が配り続けるので `docker compose stop`。`Swarm.ConnMgr` と `Routing.Type` は `kubo::apply_config` が触らないので、利用者が Kubo の設定を直接変えれば残る、と案内した。

## 測ったこと

起動中のデモ環境（`docker/demo/demo.sh up --seed`、ミラー対象 3 人・4 サイト、`poll_interval` 既定 `5m`、relay は TLS なしの `ws://`）で `docker stats` を見た。

- `mirror`（`swing up`）のメモリは約 10MB。
- relay コンテナの送受信は、起動から約 14 時間（seed を含む）で合計約 1.5MB。ここから relay との通信を 1 日約 2MB とした。
- `ipfs` コンテナは `--offline` なので、メモリ（約 56MB）は公開 IPFS につないだときの参考にならない。README には使っていない。
