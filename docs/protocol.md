# SWING プロトコル定義

この文書は SWING の相互ミラー関係を Nostr と IPFS の上でどう表現するかを、実装に依存しない形で定義する。他のクライアントやエージェントを実装する人向けの仕様であり、この Rust 実装の設定キー・CLI・`state.json`・Kubo の詳細には触れない。この実装が実際に何をどう検証しているかは [`architecture.md`](architecture.md) を参照。将来の拡張・予約 kind は [`extensions.md`](extensions.md) を参照。

キーワード「〜しなければならない」「〜すべきである」「〜してもよい」は、それぞれ RFC 2119 の MUST / SHOULD / MAY に対応する。

## 1. 目的と用語

SWING は、個人サイトの運営者同士が互いのサイトを自発的に保存・配送し合うための相互ミラーの仕組みである。中央の保存サーバーや参加者データベースを置かず、Nostr で「誰のサイトを保存するか」を各参加者が表明し、IPFS で実データを保存・配送する。

- 作者: サイトの内容を作り、その最新版を Nostr 上で表明する Nostr 公開鍵の主体。
- ミラー参加者: 他の作者のサイトを保存する意思を Nostr 上で表明し、実際に IPFS でデータを保持する主体。1 つの主体が作者とミラー参加者を兼ねてよい。
- サイト: ある作者が公開する 1 つの静的コンテンツの集合。`pubkey + kind + d タグ` の組で識別される。
- 版: あるサイトのある時点の内容。IPFS の 1 つのディレクトリ root CID に対応する。

## 2. 前提

SWING は既存の Nostr と IPFS の仕組みにそのまま乗る。独自の Relay や独自の IPFS ネットワークを要求しない。

### Nostr

- NIP-01 の addressable event（`kind` が 30000–39999 の範囲で、`pubkey + kind + d タグ` の組が同一なら同一イベント系列とみなされ、`created_at` が最大のものが有効になる仕組み）を前提とする。
- NIP-51 の一般的な Follow Set / リスト（`kind 30000`、`d` タグで区別される名前付きリスト、`p` タグで公開鍵を列挙する）を前提とする。
- NIP-05（DNS ベースの識別子検証）は任意である。使う場合は NIP-05 の仕様に従う。
- NIP-31（`alt` タグによる非対応クライアント向けの説明）は任意である。
- NIP-40（`expiration` タグによる有効期限）をレプリカ報告で使う。relay が NIP-40 に対応していなくても、受信側が期限を判定する。

### IPFS

- サイトの内容は IPFS 上のディレクトリとして表現され、その root CID で参照される。
- CIDv1 を推奨する。CIDv0 も受理してよい（MAY）。
- CID はディレクトリの root を指す。ファイル単体の CID をサイトの CID として扱わない。

## 3. 共通の規則

この節の規則と定義は、以降の節で参照する。どのイベントに適用するかは各規則に記す。

### 3.1 署名の検証

- ミラー対象リスト（第 4 節）・サイトイベント（第 5 節）・レプリカ報告（第 8 節）を受信した側は、イベントの署名を検証しなければならない（MUST）。署名が不正なイベントは破棄しなければならない（MUST）。

### 3.2 最新のイベントの選び方

- 同一の `pubkey + kind + d` を持つイベントのうち、`created_at` が最大のものが最新である。`created_at` が等しい場合は、NIP-01 の置き換え規則どおり `id` が辞書順で最も小さいものを最新とする。この文書で「NIP-01 の置き換え規則」と書くときはこの順序を指す。

### 3.3 未来の時刻

- `created_at` が受信側の現在時刻より先で、時計のずれとして許容できる範囲を超えるミラー対象リスト・サイトイベント・レプリカ報告は、無視すべきである（SHOULD）。`created_at` は作者や報告者の自己申告であり、受信側のレート制限や保持期間の判定を避けるために先の時刻を入れられるからである。

### 3.4 文字と数値の表記

- 「制御文字」は Unicode の Cc（C0 制御文字 U+0000–U+001F、DEL U+007F、C1 制御文字 U+0080–U+009F）を指す。
- 「見えない書式文字」は、ソフトハイフン（U+00AD）、アラビア文字の方向マーク（U+061C）、モンゴル語の母音区切り（U+180E）、ゼロ幅文字と方向マーク（U+200B–U+200F）、行・段落区切りと双方向の埋め込み・上書き（U+2028–U+202E）、語結合子・不可視演算子と双方向の分離（U+2060–U+2069）、BOM（U+FEFF）、行間注釈の制御（U+FFF9–U+FFFB）、タグ文字（U+E0000–U+E007F）を指す。表示上は見えないか並びを入れ替えるため、見た目が同じ別のサイト識別子やタイトルを作れてしまう。
- 「10 進整数」は、ASCII の数字 `0`–`9` だけからなり、符号・空白・小数点を含まない文字列を指す。

### 3.5 CID の比較とコーデック

- サイトイベントとレプリカ報告の `cid` タグが指す「サイトのディレクトリ root」は UnixFS のディレクトリであり、UnixFS のディレクトリ root は常に dag-pb なので、他のコーデック（raw、dag-cbor など）は構文として妥当な CID であってもこの制約を満たせない。CIDv0 は常に dag-pb を意味する。
- CIDv0 と、同じマルチハッシュ・同じ dag-pb コーデックを持つ CIDv1、および同じ CIDv1 の異なる multibase 表記（例: base32 と base58btc）は、いずれも同じ版を指す。受信側は、サイトイベントとレプリカ報告の `cid` タグを、文字列としてではなく、デコードした値で比較すべきである（SHOULD）。

## 4. ミラー対象リスト（Follow Set）

ミラー参加者は、自分が保存したい相手を NIP-51 Follow Set で表明する。

- `kind` は `30000` である。
- `d` タグの値は `swing` である。
- 保存対象の公開鍵は `p` タグ（値は hex 公開鍵）で列挙する。1 つの Follow Set に複数の `p` タグがあってよい。
- 同一 author の複数のイベントのうち、`created_at` が最大のものだけが有効な Follow Set である。それより古いイベントは無視しなければならない（MUST）。
- `created_at` が先の時刻の Follow Set は、第 3.3 節に従って無視すべきである（SHOULD）。
- NIP-51 の暗号化された private 部分（`content` が非空の場合の復号後の内容）の扱いはこのプロトコルでは規定しない。受信側はこれを無視してよい（MAY）。
- `p` タグ以外のタグ（例えば `title` のような人間向けの説明）は自由に付けてよく、プロトコル上の意味を持たない。
- 誰でも大量の `p` タグを持つ Follow Set を発行できるため、受信側は 1 つの Follow Set から読み取る `p` タグの数に上限を設けてもよい（MAY）。上限を超えた分をどう扱うか（無視する・警告するなど）は各受信側のローカルなポリシーに委ねる。

## 5. サイトイベント

作者は、自分のサイトの現在の版を addressable event で表明する。

### 5.1 形式

- `kind` は `35980` である。
- addressable event なので `pubkey + kind + d` の組が 1 つのサイトを識別する。
- タグ:
  - `d`（必須）: サイト識別子。通常は運営しているドメイン名を使うが、プロトコル上はドメイン以外の文字列でもよい。空文字であってはならない（MUST NOT）。253 バイトを超えてはならない（MUST NOT）。制御文字と見えない書式文字（第 3.4 節）を含んではならない（MUST NOT）。`d` にドメイン名を使う場合、作者はそのドメインのルートを管理しているべきである（SHOULD）。そうでない場合はドメイン名の形をしない識別子を使うべきである（SHOULD）。NIP-05 検証は `d` がドメイン名の形をしているときにのみ意味を持つ。
  - `cid`（必須）: サイトのディレクトリ root を指す有効な CID。
  - `url`（任意）: サイトの通常の http または https の URL。制御文字を含んではならない（MUST NOT）。
  - `size`（任意）: サイトデータの合計バイト数を表す 10 進整数（第 3.4 節）の文字列。Kubo でいう `files/stat` の `CumulativeSize` に相当する量であり、具体的な計測方法は実装に委ねる。
  - `title`（任意）: サイトの表示用タイトル。256 バイトを超えてはならない（MUST NOT）。制御文字と見えない書式文字（第 3.4 節）を含んではならない（MUST NOT）。
  - `alt`（任意）: NIP-31 の説明。
- `content` は作者が読者向けに書く更新メモ（プレーンテキスト）である。空文字でもよい（MAY）。作者は更新メモを短く保つべきである（SHOULD）。
- 作者は新しい版を出すとき、前の版より大きい `created_at` を付けるべきである（SHOULD）。そうすれば、どの受信側でも同じ版が現在の版になる（第 5.2 節）。

### 5.2 受信側の扱い

署名の検証は第 3.1 節に従う。

- 受信側は、自分のミラー対象リストに含まれる pubkey が author であるサイトイベントのみを保存対象として受理しなければならない（MUST）。リストに含まれない pubkey からのイベントは無視しなければならない（MUST）。
- 受信側は、`cid` タグが妥当な CID として解釈できることを検証しなければならない（MUST）。解釈できないイベントはイベント全体を拒否しなければならない（MUST）。
- 受信側は、`cid` タグのコーデックが dag-pb であることを検証しなければならない（MUST）。理由は第 3.5 節のとおりである。コーデックが dag-pb でないイベントはイベント全体を拒否しなければならない（MUST）。
- `cid` タグの比較は第 3.5 節に従う。
- 受信側は、取得後に `cid` の root が実際に UnixFS のディレクトリであることを確認すべきである（SHOULD）。ディレクトリでなければその版を保存すべきではない（SHOULD NOT）。コーデックの検証は構文上の必要条件に過ぎず、dag-pb のノードがディレクトリではなくファイルであることもあるため、取得後の確認が要る。
- 受信側は、`d` タグが第 5.1 節の制約（非空・253 バイト以下・制御文字と見えない書式文字なし）を満たすことを検証しなければならない（MUST）。満たさないイベントはイベント全体を拒否しなければならない（MUST）。
- `url` タグが http または https の URL として解釈できない、または制御文字を含む場合、受信側はイベント全体ではなく `url` タグだけを無視すべきである（SHOULD）。URL としては妥当でも制御文字は端末やログに影響するので、表示前に無害化するか、最初から無視すべきである（SHOULD）。
- `title` タグが第 5.1 節の制約（256 バイト以下・制御文字と見えない書式文字なし）を満たさない場合、受信側はイベント全体ではなく `title` タグだけを無視すべきである（SHOULD）。
- `title` は作者の自己申告であり、受信側は信頼してはならない（ドメインや NIP-05 検証結果と違い、なりすましに使える）。受信側はこれを保存するかどうかの判断に使ってはならない（MUST NOT）。表示する受信側はマークアップを無害化し、`d` など検証可能な識別子と併記すべきである（SHOULD）。
- 受信側は `content` を保存するかどうかの判断に使ってはならない（MUST NOT）。端末や HTML に表示する受信側は、制御文字やマークアップを無害化すべきである（SHOULD）。受信側は、長すぎる `content` をイベント全体ではなく更新メモだけ無視してよい（MAY）。
- 受信側は、`d` タグがドメイン名の形をしている場合に限り、NIP-05 によって `d`（ドメイン）と author の pubkey の関連を確認してもよい（MAY）。これは任意の追加検証であり、確認できなかった場合やドメイン名の形をしていない場合に何をするか（保存を続ける・警告する・拒否するなど）は各受信側のローカルなポリシーに委ねる。

現在の版:

- 同一の `pubkey + kind + d` を持つイベントのうち、NIP-01 の置き換え規則（第 3.2 節）で最新のものが現在の版である。
- `created_at` が既知の有効な版より古いイベントは無視すべきである（SHOULD）。
- `created_at` が既知の有効な版と等しく `id` が異なるイベントについて、受信側は第 3.2 節の規則どおり `id` の小さい方を現在の版として置き換えてもよいし、既に受け入れた（保存した）版を保ってそのイベントを無視してもよい（MAY）。保存済みの版を同じ時刻の書き直しで取り替えないのは、受信側のローカルな選択として許される。
- `created_at` が先の時刻のサイトイベントは、第 3.3 節に従って無視すべきである（SHOULD）。この判定は、保存するかどうかだけでなく、どれを「現在の版」として扱うか（表示・レプリカ集計・ミラー対象の選択を含む、あらゆる場面での最新版の選び方）にも適用すべきである（SHOULD）。先の時刻を入れたイベント 1 件だけで、保存はさせずに表示や集計の上で現在の版を騙れてしまっては、保存を拒む意味が薄れる。

### 5.3 更新の告知

- 作者は、サイトイベントとは別に、更新を SWING に対応していないクライアントの読者へ知らせる通常の投稿（NIP-01 の `kind 1`）を出してもよい（MAY）。出す場合は、そのサイトを指す `a` タグ（`35980:<作者pubkey hex>:<d>`）を付けるべきである（SHOULD）。NIP-24 のハッシュタグ（`t` タグ）を付けてもよい（MAY）。この投稿はサイトの版を表さないので、受信側はこれを保存や現在の版の判断に使ってはならない（MUST NOT）。

## 6. 保存ポリシー

実際にどのサイトをどれだけの期間・容量で保存するかは、各ミラー参加者のローカルな設定であり、このプロトコルでは規定しない。ただし、ミラー参加者は以下の観点で何らかの上限を持つべきである（SHOULD）。

- 保存する容量の上限（全体、またはサイト単位)
- 保持する版の世代数、または保持する期間の上限
- 同一サイトからの更新を受理する頻度の上限

これらの具体的な値や判定順序は各実装の裁量である。

## 7. 相互関係（Webring）の解釈

ある参加者 A のミラー対象リストに B の pubkey が含まれ、かつ B のミラー対象リストに A の pubkey が含まれる場合、A と B は相互にミラーしている関係にあると解釈する。この相互関係を検出・可視化する方法（複数の Relay を横断した Follow Set の収集など）はこのプロトコルでは規定しない。

ある参加者の Follow Set に別の参加者の pubkey が含まれていることは、その別の参加者が名指しした側と何らかの関係にあることを意味しない。Follow Set は名指しした側の自己申告であり、名指しされた側がそれに同意したわけでも、関与したわけでもないからである。受信側は、一方だけが相手を Follow Set に入れている状態を、双方向の関係であるかのように提示すべきではなく（SHOULD NOT）、双方向になって初めて相互の関係として示すべきである（SHOULD）。

## 8. レプリカ報告

ミラー参加者は、あるサイトのどの版を今保存しているかを addressable event で報告する。作者が自分のサイトを保存している場合も、作者自身が報告してよい（MAY）。

### 8.1 形式

- `kind` は `35981` である。
- タグ:
  - `d`（必須）: `<作者の hex 公開鍵>:<サイトの d>`。hex は小文字 64 文字である。1 人の報告者はサイトごとに 1 つの系列を持つ。
  - `a`（必須）: `35980:<作者の hex 公開鍵>:<サイトの d>`。`d` と同じサイトを指さなければならない（MUST）。
  - `p`（推奨）: 作者の hex 公開鍵。報告者は付けるべきである（SHOULD）。作者が自分のサイトへの報告をまとめて取得するために使う。
  - `cid`（0 個以上）: 報告者が今保存している版の CID。1 つのタグに 1 つの CID を入れる。保存している版をすべて並べるべきである（SHOULD）。
  - `expiration`（推奨）: NIP-40 の有効期限。
  - `alt`（任意）: NIP-31 の説明。
- `content` は空文字である。受信側は、長い `content` を持つ報告を無視してよい（MAY）。
- `cid` タグが 1 つも無い報告は「このサイトをもう保存していない」ことを表す。保存をやめた報告者は、NIP-09 の削除ではなく、この形の報告で以前の報告を置き換えるべきである（SHOULD）。NIP-09 を処理しない relay でも置き換えは働くからである。
- 報告者は、有効期限が切れる前に報告を出し直すべきである（SHOULD）。止まった報告者の報告は期限切れで数えられなくなる。
- 報告は自己申告であり、実際に配送できることを保証しない。

### 8.2 受信側の扱い

- 同じ報告者・同じ `d` の報告のうち、NIP-01 の置き換え規則（第 3.2 節）で最新のものだけを使わなければならない（MUST）。
- `d` を最初の `:` で作者とサイトの `d` に分け、作者が正しい hex 公開鍵でない、サイトの `d` が第 5.1 節の制約を満たさない、`a` が `d` と一致しない、`cid` のどれかが妥当な CID として解釈できない、`cid` のどれかのコーデックが dag-pb でない、のいずれかに当たる報告は無視しなければならない（MUST）。
- `cid` タグの比較は第 3.5 節に従う。同じ版を別の表記で報告した `cid` タグは重複ではなく同一の版として扱う。
- `expiration` タグが存在するのに 10 進整数（第 3.4 節）として解釈できない報告は無視しなければならない（MUST）。
- `created_at` が先の時刻の報告は、第 3.3 節に従って無視すべきである（SHOULD）。
- `expiration` を過ぎた報告は数えてはならない（MUST NOT）。
- 受信側は、`expiration` の有無や値によらず、`created_at` から一定期間が経った報告を数えるのをやめてよい（MAY）。`expiration` は報告者の自己申告であり、報告を出し直す（再署名する）ことだけが報告者がまだ生きていることの証拠になるからである。報告者は、この期間より前に報告を出し直すべきである（SHOULD）。
- あるサイトのレプリカ数は、そのサイトの現在の版（第 5.2 節）の CID を `cid` タグに含む報告の、報告者の数である。報告者がそのサイトの作者をミラー対象リスト（第 4 節）に入れているかを確かめるかどうかは、受信側に委ねる。
- 報告も誰でも捨て鍵で大量に発行できるため、受信側は 1 つのサイトについて処理する報告の数に上限を設けてもよい（MAY）。上限を超えた分を落とす場合、`created_at` が新しい報告を優先すべきである（SHOULD）。古い報告者ほど、有効期限内に出し直す機会が既にあったはずだからである。ただし、下記の信頼できる報告者（作者自身や、作者か受信側のミラー対象リストに含まれる報告者）の報告を先に残し、その中と残りの中でそれぞれ `created_at` の新しい順に残すことも、受信側のローカルなポリシーとして許される（MAY）。relay から取得する件数にも上限を付ける受信側は、捨て鍵の報告で下記の信頼できる報告者の報告が押し出されないよう、信頼できる報告者に絞った取得を別に行ってもよい（MAY）。
- 受信側は、作者ごとの報告の取得や、自分のサイトへの報告の通知などで、`p` タグに頼ってよい（MAY）。`p` タグを持たない報告は、そうした取得で見つからなくてもよい。
- 報告者が誰であるかも自己申告であり、報告者自身の Follow Set にその作者が含まれていると報告者が主張しても、それだけでは根拠にならない（第 7 節）。受信側は、レプリカ数を数える、または示す際、報告者が作者のミラー対象リストか受信側自身のミラー対象リストのいずれかに含まれる報告だけを数え、それ以外の報告は未検証なものとして別に示してもよい（MAY）。

## 9. サイトイベントの送り直し

作者が送るのをやめた後で relay からサイトイベントが消えると、内容をミラーしている参加者がいても、新しい参加者はそのサイトを見つけられない。この節は、ミラー参加者が作者のサイトイベントを relay へ送り直すときの規則を定める。

### 9.1 送り直す条件

- ミラー参加者は、自分が保存している版のサイトイベントを持たない relay へ、作者が署名したイベントを改変せずにそのまま送り直すべきである（SHOULD）。送り直すのは自分が保存している版のイベントだけとする。その relay が同じイベントを持っていれば、その relay へは送り直すべきではない（SHOULD NOT）。
- どれかの relay が、NIP-01 の置き換え規則（第 3.2 節）でそれより新しい版（作者が署名し、第 3.3 節で無視しないもの）を持っていれば、作者は新しい版で置き換えて古い版を取り下げたものとみなし、どの relay へも送り直すべきではない（SHOULD NOT）。自分の保存ポリシー（第 6 節）でその新しい版を保存しなかった場合も同じである。ミラー参加者はこのことを覚えておき、後で新しい版が relay から消えても、それより古い版を送り直すべきではない（SHOULD NOT）。

### 9.2 作者による取り下げ

- 作者がそのイベントを NIP-09 の削除要求（`kind 5`）で取り下げているとき、ミラー参加者はそれを送り直すべきではない（SHOULD NOT）。取り下げとみなすのは、作者自身が出した削除要求のうち、`e` タグがそのイベントの `id` を指すもの、または `a` タグがそのサイト（`35980:<作者pubkey hex>:<d>`）を指し、削除要求の `created_at` がそのイベントの `created_at` 以上のもの（NIP-09）である。NIP-09 に従ってイベントを消した relay は、送り直す側からは「そのイベントを持たない relay」に見えるので、この確認をしないと取り下げたサイトを生き返らせてしまう。
- 削除要求の `created_at` が第 3.3 節の許容を超えて先でも、作者自身が出したものなら取り下げとみなしてよい（MAY）。ただし `a` タグの取り下げの範囲は、受信側の現在時刻に許容を足した時刻までとすべきである（SHOULD）。先の時刻にすれば、まだ出していない版まで前もって取り下げられてしまうからである。
- 削除要求も relay から消えることがある。ミラー参加者は、取り下げを一度確かめたら、そのことを覚えておき、削除要求が見つからなくなっても取り下げられたイベント（`e` なら同じ `id`、`a` なら削除要求の `created_at` 以下のそのサイトのイベント）を送り直すべきではない（SHOULD NOT）。取り下げた後に作者が出した新しい版は、取り下げに当たらないので送り直してよい。取り下げは送り直すかどうかだけに関わり、受信した版を保存するかどうか（第 6 節）は変えない。

### 9.3 削除要求の確かめ方

- 送り直す前に削除要求を確かめるときは、その削除要求を見つけられなかった relay を「取り下げが無い」とみなすべきではない。削除要求の取得に答えなかった relay には、その回は送り直すべきではない（SHOULD NOT）。答えが `limit` に達した relay には、返った削除要求の境（NIP-01 で relay は新しい順に返し古い方を切るので、`limit` 件目の `created_at`）より新しくない版を、その回は送り直すべきではない（SHOULD NOT）。境と同じ `created_at` の版も、同じ時刻の削除要求が切られたかもしれないので送り直すべきではない。NIP-09 に従ってイベントを消した relay は削除要求を持っていることが多く、送り直す相手もその relay なので、そこからの答えを確かめずに送るのが最も危うい。

### 9.4 確実に取り下げたい作者へ

- NIP-09 に従うかどうかは relay ごとに異なり、ミラー参加者が削除要求を見つけられる保証も無い。確実に取り下げたい作者は、より大きい `created_at` を持つ新しい版でサイトイベントを置き換えるべきである（SHOULD）。置き換えた版は NIP-01 の置き換え規則（第 3.2 節）で古い版より優先されるので、古い版が送り直されても現在の版には戻らない。
