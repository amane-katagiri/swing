# IPFS で配りやすい静的サイトにする

`swing publish` で自分のサイトを公開する人向けの手引き。SWING のミラーは、あなたのサイトを「ある時点のディレクトリの丸ごとのコピー」として保存し、IPFS のゲートウェイ越しに配る。普通の Web サーバーで動いているサイトがそのままでは壊れたり、保存してもらえなかったりする点を、チェックリストの形でまとめる。

ここに出てくる上限の値は、ミラーする各参加者のローカル設定の既定値にすぎない。各キーの意味と既定値の正本は README の[設定一覧](../README.md#設定一覧)と [`../swing.example.toml`](../swing.example.toml)、判定の順序は [`architecture/agent.md#ポリシー判定policyrs`](architecture/agent.md#ポリシー判定policyrs)、publish の処理は [`architecture/cli.md#publish`](architecture/cli.md#publish)。この文書と食い違うときはそちらに従う。

## チェックリスト

### 中身

- [ ] 公開してよいものだけが入っている
- [ ] ドットファイル（`.git`・`.env` など）が入っていない
- [ ] ソースマップ・ビルド前のソース・`node_modules` が入っていない

### サイズ

- [ ] 1 版の合計が数百 MB 程度までに収まっている
- [ ] 画像・動画・フォントを配信用に縮めている
- [ ] 大きなファイルを、更新のたびに作り直していない

### 外部への依存

- [ ] フォント・CSS・JavaScript を CDN から読み込んでいない
- [ ] 画像や動画の本体が、サイトのディレクトリの中にある
- [ ] 表示に外部の API やサーバーの処理が要らない

### リンクとパス

- [ ] サイト内のリンクと読み込みが相対パスになっている
- [ ] 自分のドメインの絶対 URL でサイト内を指していない
- [ ] 拡張子なしの URL やサーバー側の書き換えに頼っていない
- [ ] ファイル名の大文字小文字をリンクと揃えている

### 再現性と更新

- [ ] 同じ内容からは、バイト単位で同じ出力になる
- [ ] 中身が変わっていなければ publish しない
- [ ] 細かい修正はまとめて、1 回の publish にしている

以下、各項目の理由と確かめ方。

このうちドットファイル・1 版のサイズ・前回と同じ内容かどうかの 3 つは、`swing publish`（ダッシュボードの公開画面も）が自動で確かめる。項目ごとに `off`（確かめない）・`warn`（表示して続ける）・`require`（引っかかったら止める）を選べる。フラグ・設定のキーと既定値は README の「[自分のサイトを公開する](../README.md#自分のサイトを公開する)」、判定の細部は [`architecture/cli.md#publish`](architecture/cli.md#publish)。自動の確認は機械的に分かるものだけなので、残りの項目は自分で確かめる。

## 中身

### 公開したものは取り消せない

ミラーする参加者は、新しい版が来ても古い版を `keep_versions`（既定 5）個・`keep_days`（既定 365 日）まで残す。また、IPFS に出たデータは誰でも取得してコピーできる。一度 publish した内容は、次の版で消しても他人の手元に残ると考える。下書き・個人情報・鍵・トークンが出力に紛れ込んでいないかを、publish の前に確かめる。

### ドットファイルも含まれる

`swing publish <DIR>` は `DIR` の下のファイルをすべて追加する。`ipfs add` と違い、名前が `.` で始まるファイルやディレクトリも除外しない。シンボリックリンクは辿って、リンク先の中身を追加する。ただし、リンク先が `DIR` の外にあるシンボリックリンク（`key.txt -> ~/.ssh/id_ed25519` など）が 1 つでもあると、確認の設定にかかわらず何も追加せずに止まる。`DIR` の外のものを載せたいときは、リンクではなく `DIR` の中にコピーする。

同じく確認の設定にかかわらず、`DIR` の中に SWING の設定ファイル（`swing.toml`）、状態ディレクトリ（`[agent].state_dir`、既定は設定ファイルの隣の `data`）、Kubo のリポジトリ（`[kubo].repo`）のどれかがあるとき、また `DIR` が状態ディレクトリか Kubo のリポジトリの中にあるときも、何も追加せずに止まる。これらには Nostr の秘密鍵・ダッシュボードのトークン・Kubo の秘密鍵が入っているため。`swing.toml` を置いたディレクトリをそのまま公開せず、サイトは別のディレクトリ（`public/` など）に分ける。

リポジトリをそのまま渡すと `.git` や `.env` まで公開される。ビルドの出力先（`public/` や `dist/` など）だけを渡す。NIP-05 に使う `/.well-known/nostr.json` はここに入っていてよい。

publish は既定で、名前が `.` で始まるファイルやディレクトリを見つけると、追加する前に止まって一覧を出す。`.well-known` や `.nojekyll` のように意図して置くものは見逃す一覧（`[publish].dotfiles_allow`）に入っている。見逃すのはその名前自身だけで、その下にある `.` で始まるもの（`.well-known/.env` など）は止める。ほかにも意図して置くものがあれば、確認そのものを切るのではなく、その名前を一覧に足す（一覧を指定すると既定の一覧を置き換えるので、既定の名前も必要なら並べ直す）。

ソースマップ（`*.map`）・ビルド前のソース・`node_modules` も、閲覧に要らないのに容量を食い、ソースを公開する意図がなければ中身も漏れる。

## サイズ

### ミラーの上限は版ごとの丸ごとの大きさで数える

ミラーする側は、版ごとに実際に取得したデータ量で上限を判定する（イベントの `size` タグは信用しない）。既定では、

- 1 版が `max_update_size`（2 GiB）を超えると保存されない
- 1 サイトの全版の合計が `max_per_site`（10 GiB）を超えると古い版から消され、新しい版だけで超えるなら保存されない
- 1 アカウントの全サイトの合計が `max_per_account`（20 GiB）を超える更新は保存されない

全版の合計は、版と版で共通するファイルも版ごとに数える（実際のディスク使用量は共通部分を 1 回しか持たないが、上限の判定は多めに見積もる側に倒している）。1 版が 2 GiB なら 5 版で 10 GiB に達するので、古い版はほとんど残らない。上限は参加者ごとに違い、既定より小さくしている人もいる。多くの人に保存してもらうには、1 版を数百 MB 程度までに抑えるのが目安。

publish の出力の `Size:` が 1 版の大きさ。ミラーした人の手元で保存されたかは `swing replicas` で確かめられる。

publish は、ファイルの合計が 512 MiB を超えると、追加する前に警告を出す（既定では止めない）。この値は上の「数百 MB」を固定の数にした目安で、ミラーする側の判定とは関係しない。

### 画像・動画・フォントを縮める

容量の大半はたいてい画像と動画。

- 表示する大きさに合わせて縮小し、WebP や AVIF など圧縮の効く形式にする
- 写真のメタデータ（撮影位置など）を消す。容量の節約にもなり、上の「取り消せない」の対策にもなる
- 動画は長さと解像度を絞る。長いものは SWING の外に置き、リンクだけにすることも考える
- フォントは使う文字だけに絞る（サブセット化）。日本語フォントは丸ごと入れると 1 書体で数 MB になる

### 変わっていないファイルは変えない

IPFS はファイルをブロックに分けて、中身のハッシュで管理する。ミラーする側が新しい版を取得するとき、手元にすでにあるブロックは取り直さないので、前の版からバイト単位で変わっていないファイルは転送もディスクも増やさない。

逆に、中身が同じでも毎回少しでも違うバイト列で作り直すファイル（下の[再現性](#同じ内容からは同じ出力にする)を参照）は、更新のたびに丸ごと取り直される。大きなファイルほど影響が大きい。

## 外部への依存

ミラーが保存するのは `swing publish` に渡したディレクトリの中だけ。外部のサーバーから読み込んでいるものは保存されず、そのサーバーが止まったり中身を変えたりすれば、ミラーされたサイトも一緒に壊れる。元のサイトが無くなっても読めることが SWING の目的なので、表示に要るものはディレクトリに入れる。

- Web フォントや CSS・JavaScript のライブラリを CDN から読み込んでいれば、ファイルをダウンロードしてサイトに同梱する（ライセンスを確認する）
- 画像や動画を外部のサービス（画像ホスティングや SNS）に置いて貼っているなら、本体をサイトに入れる
- 埋め込み（動画プレイヤー・SNS の投稿・地図など）は、無くなっても本文が読めるように、リンクや静止画を添える
- アクセス解析や広告のスクリプトは、ミラー経由の閲覧ではたいてい意味を持たず、読者を外部に送るだけなので、入れるなら元のサイトにだけ入れることも考える
- コメント欄・フォーム・サイト内検索など、サーバーの処理が要る機能はミラーでは動かない。本文の表示がそれに頼らないようにする

## リンクとパス

### サイト内は相対パスで指す

ミラーされたサイトは、いろいろな URL で開かれる。

- `https://<ゲートウェイ>/ipfs/<cid>/`（パス形式のゲートウェイ）
- `https://<cid>.ipfs.<ゲートウェイ>/`（サブドメイン形式のゲートウェイ。ダッシュボードのリンクが指すローカルの Kubo も、既定ではこちらに転送する）
- DNSLink を設定した自分のドメイン

`/css/style.css` のように `/` で始まるパスは、パス形式のゲートウェイではゲートウェイ自体のルートを指してしまい、読み込めない。`css/style.css` や `../css/style.css` のように、そのページからの相対パスで書く。静的サイトジェネレーターの多くは、ベース URL や相対パスの出力を設定で切り替えられる。`<base href="/">` も同じ理由で使わない。

`https://example.jp/about/` のように自分のドメインの絶対 URL でサイト内を指すと、ミラーで開いた読者が元のサイトに飛ばされ、元のサイトが無くなればリンク切れになる。`<link rel="canonical">` や OGP の `og:url` のように、元の URL を示すこと自体が目的のものは絶対 URL のままでよい。

### サーバー側の機能に頼らない

ゲートウェイはディレクトリの中身をそのまま返すだけで、Web サーバーの設定にあたるものは持たない。

- `/about` で `about.html` を返すような拡張子の省略はできない。`about.html` と書くか、`about/index.html` を置いて `about/` と書く
- `.htaccess` や、ホスティングサービス独自の設定ファイル（リダイレクト・ヘッダーの指定など）は効かない
- すべてのパスを `index.html` に向けるシングルページアプリのルーティングは、ハッシュ（`#/about`）方式にするか、ページごとに HTML を出力する
- 独自の 404 ページやリダイレクトは、Kubo のゲートウェイでは `_redirects` ファイルで書けるが、効くのはサブドメイン形式と DNSLink で開いたときだけで、パス形式のゲートウェイでは無視される。無くても困らない範囲で使う

### ファイル名

ゲートウェイはファイル名の大文字小文字を区別する。大文字小文字を区別しない環境（Windows や macOS の既定）で確かめていると、`Image.PNG` を `image.png` で指していても気づかない。ファイル名は英小文字・数字・ハイフンにしておくと、URL のエンコードの違いでも困らない。

### ブラウザの保存領域をあてにしない

パス形式のゲートウェイでは、そこで開くすべてのサイトが同じオリジンになる。`localStorage` や Cookie、Service Worker は他のサイトと共有され、読み書きもされうる。設定の保存程度ならよいが、それが無いと表示できない作りや、他人に見られて困るものを置く作りにはしない。

## 再現性と更新

### 同じ内容からは同じ出力にする

IPFS の CID は、ディレクトリの中のファイル名と中身だけから決まる（SWING の publish は更新日時やパーミッションを含めない）。同じ出力なら、何度 publish しても同じ CID になる。

ビルドのたびに出力がずれると、中身は変えていないのに CID が変わり、ミラーする側には別の版として届く。よくある原因は次のとおり。

- 「最終更新: ビルドした日時」のような、ビルド時刻の埋め込み
- 乱数やビルド番号を含むファイル名・クエリ文字列（`app.3f9a1c.js` のような名前は、中身のハッシュから作られるものなら問題ない）
- 実行のたびに順序が変わる一覧（記事一覧・サイトマップ・RSS）
- 画像の変換を毎回やり直し、変換ツールの設定や版の違いで結果が変わる

確かめるには、同じソースから 2 回ビルドして、出力ディレクトリを `diff -r` で比べる。差が出なければよい。日付を出したいときは、ビルドした時刻ではなく記事に書いた日付やコミットの日時を使う。

### 変わっていなければ publish しない

同じ CID のサイトイベントを出し直しても、ミラーする側は同じ CID を見送るので保存量は増えないが、relay に意味の無い更新が流れ、自分の手元では同じ内容の版が `[publish].keep_versions` の枠を埋めて、本当に古い版が押し出される。

`swing publish` は既定で、追加した CID を relay 上の自分の最新版と比べ、同じなら追加した版を消して、イベントを出さずに `Unchanged; not published.` で終わる。このときの終了コードは 0 なので、CI などで毎回 publish を実行してもよい。relay から前の版を取れなかったときは止めずに publish するので、確実に避けたいなら、これまでどおり出力が前回から変わったときだけ実行する（出力を前回のものと `diff -r` で比べる、生成物をリポジトリで管理して差分を見る、など）。ビルドの出力がずれていると CID も変わるので、この確認では止まらない（上の[再現性](#同じ内容からは同じ出力にする)を参照）。

### 更新はまとめる

ミラーする側は、同じサイトの版を `min_update_interval`（既定 1 時間）より短い間隔では取り込まない。間隔が空くまで待ってから、その時点の最新版だけを取り込むので、その間の版はミラーには残らない。

また、新しい版が来るたびに古い版は `keep_versions`（既定 5）個を超えた分から消える。誤字の修正を 1 つずつ 5 回 publish すると、その前の内容はもうミラーに残らない。ミラーが持つ版を「読み返せる過去の姿」として残したいなら、細かい修正はまとめて 1 回にし、publish の頻度は多くても 1 日に数回程度にとどめる。

更新メモ（`-m`）はミラーする人の画面や Nostr クライアントに出るので、版ごとに何を変えたかが分かるように書くとよい。
